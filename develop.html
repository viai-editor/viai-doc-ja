Vim の開発。                                            development

この文章は、Vim のこれからの開発に関わりたい人にとって重要である。

1. 設計の目標           design-goals

ソースコードの概要については、"src" ディレクトリの README.txt ファイルを参照。

Vim はオープンソースソフトウェアである。誰もが Vim の改良を助けるために貢献す
ることが奨励されている。パッチを送るには、unified diff "diff -u" が好まれる。
github でプルリクエストを作ることもできるが、必須ではない。
http://vim.wikia.com/wiki/How_to_make_and_submit_a_patch も参照。

1. 設計の目標                                           design-goals

最も重要なものが最初に来る (おおよそ)。

Note かなりの項目が矛盾していることに注意。これは意図的である。それらの間でバ
ランスを見つけなければならない。


Vim は... Vi 互換である                                design-compatible

何よりもまず、Vim を Vi の差し替えとして使うことができるべきである。ユーザーが
望めば、Vim を互換モードで使うことができ、オリジナルの Vi との違いにはほとんど
気付かない。

例外:
- 明らかな Vi のバグは Vim では再現しない。
- Vi にはさまざまなバージョンがある。私はバージョン 3.7 (6/7/85) を基準として
  使っている。しかし、可能な場合は他のバージョンのサポートも含まれている。
  POSIX の Vi の部分は、決定的な情報源とはみなしていない。
- Vim は新しいコマンドを追加しているので、Vi に存在しなかったからといって、あ
  るコマンドが失敗することを当てにすることはできない。
- Vim には Vi にない機能がたくさんある。Vim から Vi に戻るのは問題になるが、こ
  れは避けられない。
- いくつかのものはほとんど使われない (オープンモード、クラッシュ時に電子メール
  を送ることなど)。それらは、誰かが含めるべき十分な理由を持っていて、それほど
  手間がかからない場合にのみ含める。
- いくつかの項目については、Vi 互換性を保つべきかどうかに議論の余地がある。こ
  れらにはオプションフラグがある。


Vim は... 改良されている                               design-improved

Vim の改良 (IMproved) 部分は、まったく別のエディタになることなく、Vim をより良
い Vi にするべきである。拡張は「Vi の精神」で行う。
- できる限りキーボードを使う。マウスには 3 本目の手が必要だが、私たちにはそれ
  がない。多くの端末にはマウスがない。
- それでもマウスを使う場合は、キーボードに戻る必要をなくす。マウスとキーボード
  の操作を混ぜることを避ける。
- コマンドとオプションは一貫した方法で追加する。そうしないと、人々はそれらを見
  つけたり覚えたりするのに苦労する。後でさらにコマンドとオプションが追加される
  ことを念頭に置くこと。
- 人々が知らない機能は役に立たない機能である。分かりにくい機能を追加しないか、
  少なくともドキュメントにそれが存在するというヒントを加える。
- CTRL やその他の修飾キーを使うことを最小限にする。それらはタイプしにくい。
- 初めての、または経験の浅い Vim ユーザーがたくさんいる。彼らが Vim を使い始
  め、時間をかけてさらに学ぶことを簡単にする。
- 追加できる機能に制限はない。新しい機能の選択は、(1) ユーザーが何を求めている
  か、(2) 実装するのにどれだけの労力がかかるか、(3) 誰かが実際にそれを実装する
  か、に基づいて行う。


Vim は... マルチプラットフォームである         design-multi-platform

Vim は、できるだけ多くのプラットフォームで、できるだけ多くのユーザーを助けよう
としている。
- 多くの種類の端末をサポートする。最小限の要件は、カーソルの位置決めと画面のク
  リアである。コマンドは、ほとんどのキーボードにあるキーストロークだけを使うべ
  きである。マッピングのために、キーボードのすべてのキーをサポートする。
- 多くのプラットフォームをサポートする。条件は、そのプラットフォームで Vim の
  開発を進んで行う人がいることと、それがコードを散らかすことを意味しないことで
  ある。
- 多くのコンパイラとライブラリをサポートする。誰もが別のコンパイラや GUI ライ
  ブラリをインストールできたり、それを許されていたりするわけではない。
- 人々はあるプラットフォームから別のプラットフォームへ、また GUI 版から端末版
  へと切り替える。機能は、すべてのバージョンに存在するか、少なくとも妥当な労力
  でできるだけ多くのバージョンに存在するべきである。ユーザーが効率的に作業をこ
  なすためにプラットフォームを切り替えなければならないことを避けるようにする。
- ある機能がいくつかのプラットフォームでは実現できない、または 1 つのプラット
  フォームでしか実現できないということは、それを実装できないという意味ではな
  い。[これは意図的に前の項目と矛盾しており、この 2 つはバランスを取らなければ
  ならない。]


Vim は... よく文書化されている                 design-documented

- 文書化されていない機能は役に立たない機能である。新しい機能のパッチには、ド
  キュメントが含まれていなければならない。
- ドキュメントは包括的で理解しやすいものであるべきである。例を使うことが推奨さ
  れる。
- 文章を不必要に長くしない。ドキュメントが少ないほど、項目を見つけやすい。


Vim は... 高速でサイズが小さい                 design-speed-size

Vim を使うことが、システムリソースへの大きな攻撃になってはならない。小さく速く
保つこと。
- コンピュータは毎年より速く、より大きくなっている。Vim も大きくなってよいが、
  コンピュータが大きくなるより速くではない。古いシステムでも Vim を使えるよう
  に保つ。
- 多くのユーザーは、シェルから非常に頻繁に Vim を起動する。起動時間は短くなけ
  ればならない。
- コマンドは効率的に動作しなければならない。コマンドが消費する時間は、できるだ
  け短くなければならない。役に立つコマンドは、より長くかかってもよい。
- 遅い接続で Vim を使う人もいることを忘れないこと。通信のオーバーヘッドを最小
  限にする。
- サイズをかなり増やし、多くの人に使われない項目は、無効にできる機能にするべき
  である。
- Vim は他のコンポーネントの中の 1 つのコンポーネントである。巨大なアプリケー
  ションにせず、他のプログラムとうまく一緒に動作するようにする。


Vim は... 保守しやすい                         design-maintain

- ソースコードはめちゃくちゃになるべきではない。信頼できるコードであるべきであ
  る。
- 読みやすくするために、すべてのファイルで同じレイアウトを使う coding-style。
- コメントは役に立つように使う! 関数名と引数名を書き写すのは役に立たない。それ
  らが何のためにあるのかを説明すること。
- 別のプラットフォームへの移植は、プラットフォームに依存しないコードをあまり変
  更せずに、簡単にできるようにするべきである。
- オブジェクト指向の精神を使う: データとコードを一緒に置く。コードの他の部分に
  広がる知識を最小限にする。


Vim は... 柔軟である                                   design-flexible

Vim は、ユーザーを特定の作業パターンに強いるのではなく、ユーザーが好みのスタイ
ルで作業することを簡単にするべきである。これは、影響の大きい項目 (例えば
'compatible' オプション) にも、細かい点にも当てはまる。デフォルトは、ほとんど
のユーザーがそのままで Vim を楽しく使えるように、慎重に選ばれている。コマンド
とオプションを使って、ユーザーの望みとその環境に Vim を合わせることができる。


Vim は... ではない                                     design-not

- Vim はシェルやオペレーティングシステムではない。Vim は、シェルやデバッガを実
  行できる端末ウィンドウを提供している。例えば、それを ssh 接続の上で行えるよ
  うにするためである。しかし、それと一緒にテキストエディタが必要ない場合、それ
  は範囲外である (代わりに screen や tmux のようなものを使うこと)。
  これを風刺的に言うと: "Emacs と違って、Vim はキッチンシンク以外のすべてを含
  めようとはしないが、Vim でキッチンシンクを掃除できると言う人もいる。;-)"
  Vim を gdb と一緒に使うには、terminal-debugger を参照。他の (古い) ツール
  は http://clewn.sf.net で見つかる。
- Vim は、すべてのプラットフォームでの一貫性を犠牲にしてまで、見た目を良くしよ
  うとする派手な GUI エディタではない。しかし、機能的な GUI の機能は歓迎され
  る。

2. 設計の決定                                           design-decisions

折り畳み

同じバッファに対して、いくつかの形式の折り畳みができるべきである。例えば、関数
の本体を折り畳んだテキストを表示するウィンドウと、関数の本体を表示する別のウィ
ンドウを持つ。

折り畳みはテキストを表示する方法である。テキスト自体を変更するべきではない。そ
のため、折り畳みは、バッファに格納されたテキスト (バッファ行) とウィンドウに表
示されるテキスト (論理行) の間のフィルタとして実装されている。


ウィンドウの命名

"window" という単語は、いくつかのものによく使われる: 画面上のウィンドウ、xterm
のウィンドウ、バッファを見るための Vim の中のウィンドウ。
混乱を避けるために、ウィンドウと呼ばれることがある他の項目には、別の名前が付け
られている。以下は関連する項目の概要である:

screen          ディスプレイ全体。GUI では 1024x768 ピクセルのようなものであ
                る。Vim シェルは画面全体か、その一部を使うことができる。
shell           Vim アプリケーション。これは画面全体 (例えば、コンソールで実行
                しているとき) か、その一部 (xterm や GUI) を覆うことができる。
window          バッファの表示。Vim には複数のウィンドウがあることができ、コマ
                ンドライン、メニューバー、ツールバーなどと一緒にシェルの中に収
                まる。


スペルチェック                                          develop-spell

スペルチェックを Vim に追加しようとしたとき、使用可能なスペルチェックのライブ
ラリとプログラムについて調査が行われた。残念ながら、さまざまな理由により、どれ
も Vim のスペルチェックエンジンとして使うのに十分な機能を提供していないという
結果になった:

- マルチバイトエンコーディングのサポートがない。同じファイルで複数の言語を使え
  るように、少なくとも UTF-8 はサポートしなければならない。
  その場で変換することは、常に可能なわけではない (iconv のサポートが必要にな
  る)。
- プログラムとライブラリについて: それらをそのまま使うには、Vim とは別にインス
  トールする必要がある。それはたいてい不可能ではないが、欠点である。
- パフォーマンス: いくつかのテストで、構文ハイライトと同じように、その場で (再
  描画中に) スペルチェックをすることが可能であることが分かった。しかし、他の
  コードで使われている仕組みはずっと遅い。例えば、Myspell はハッシュテーブルを
  使っている。ほとんどのスペルチェッカーが使っている接辞圧縮も、それを遅くして
  いる。
- aspell のような外部プログラムを使うには、通信の仕組みを用意しなければならな
  い。それを移植性のある方法で行うのは複雑である (Unix のみの場合は比較的簡単
  だが、それでは十分ではない)。そして、パフォーマンスが問題になる (多くのプロ
  セス切り替えが関わる)。
- "Etten-Leur" や "et al." のような、単語でない文字を含む単語のサポートがない
  と、それらの断片を OK とマークする必要があり、信頼性が下がる。
- 地域や方言のサポートがない。すべての英単語を受け入れ、カナダ以外の単語を異な
  る方法でハイライトすることが難しくなる。
- まれな単語のサポートがない。多くの単語は正しいがほとんど使われず、よく使われ
  る単語のスペルミスである可能性がある。
- 候補を作るためには速度はそれほど重要ではなく、別のプログラムやライブラリのイ
  ンストールを必要とすることは許容できるだろう。しかし、単語リストはおそらく異
  なり、候補が間違った単語になるかもしれない。


スペル候補                                      develop-spell-suggestions

候補を作るためには、2 つの基本的な仕組みがある:
1. 間違った単語を少し変えてみて、正しい単語とマッチするかを確かめる。または、
   正しい単語のリストを順に調べ、それらを少し変えて、間違った単語とマッチする
   かを確かめる。変更とは、文字の削除、文字の挿入、2 つの文字の入れ替えなどで
   ある。
2. 間違った単語と正しい単語の両方にサウンドフォールディングを行い、それからマッ
   チを見つける。1 つ目の仕組みと同じように、いくつかの変更を伴うこともある。

1 つ目は、タイプミスを見つけるのに適している。ハッシュテーブルで実験し、他のス
ペルチェッカーの解決策を調べた後、トライ (木構造の一種) がこれに理想的であると
いう結論になった。メモリ使用量を減らすことと、適切な変更を試せることの両方のた
めである。例えば、文字を挿入するとき、正しい単語につながる文字だけを試す必要が
ある。他の仕組み (ハッシュテーブルを使うもの) は、単語のすべての位置で、すべて
の可能な文字を試す必要がある。また、ハッシュテーブルには単語の境界を別に識別す
るという要件があるが、トライはこれを必要としない。
それにより、仕組みがずっと単純になる。

サウンドフォールディングは、単語がどう発音されるかは知っているが、どう綴られる
かを知らない場合に役に立つ。例えば、単語 "dictionary" が "daktonerie" と書かれ
るかもしれない。1 つ目の方法が試す必要のある変更の数はとても多く、その方法で正
しい単語を見つけるのは難しい。サウンドフォールディングの後、単語は "tktnr" と
"tkxnry" になり、これらは 2 文字しか違わない。

サウンドフォールディングした同等物 (発音が似た単語) で単語を見つけるには、サウ
ンドフォールディングしたすべての単語のリストが必要である。どれが最も良い方法か
を調べるために、いくつかの実験が行われた。選択肢:
1. 候補を探すときに、その場でサウンドフォールディングを行う。これは、正しい単
   語のトライを順に調べ、各単語をサウンドフォールディングし、それが間違った単
   語とどれだけ違うかを確かめることを意味する。これはメモリ使用の点ではとても
   効率的だが、長い時間がかかる。速い PC では、英語で数秒かかり、これは対話的
   な使用には許容できる。しかし、いくつかの言語では 10 秒以上かかり (例えば、
   ドイツ語、カタルーニャ語)、これは許容できないほど遅い。バッチ処理 (自動修正)
   では、すべての言語で遅すぎる。
2. サウンドフォールディングした単語にトライを使い、サウンドフォールディングな
   しで動作するのと同じように検索できるようにする。これには、サウンドフォール
   ディングした単語ごとに正しい単語のリストを覚えておく必要がある。これにより、
   マッチをとても速く見つけられるが、1 から 10 Mbyte 程度の、かなり多くのメモ
   リが必要になる。
   いくつかの言語では、元の単語リストより多くなる。
3. 2 つ目の選択肢と同様だが、接辞圧縮を使い、サウンドフォールディングした基本
   の単語だけを格納することで、メモリ量を減らす。これは Aspell が行っているこ
   とである。欠点は、サウンドフォールディングする前に間違った単語から接辞を取
   り除く必要があることで、これは単語の先頭と/または末尾の誤りによって、仕組み
   が失敗することを意味する。また、間違った単語が正しい単語とかなり違う場合は、
   遅くなる。

選ばれたのは、2 つ目の仕組みを使い、別のファイルを使うことである。こうすれば、
十分なメモリを持つユーザーはとても良い候補を得ることができ、一方でメモリが不足
しているユーザーや、スペルチェックだけで候補はいらないユーザーは、それほど多く
のメモリを使わない。


単語の頻度

候補をソートするためには、どの単語がよく使われるかを知っていると役に立つ。理論
的には、辞書の単語と一緒に単語の頻度を格納することができる。しかし、これには単
語ごとにカウントを格納する必要がある。それは単語ツリーの圧縮をかなり低下させ
る。そして、すべての言語について単語の頻度を保守するのは大変な作業になるだろ
う。また、すでにテキストの中にある単語を優先できると良いだろう。こうすれば、特
定のテキストに現れる単語が候補として優先される。

実装されたのは、表示中に見た単語を数えることである。単語のカウントをすばやく見
つけるために、ハッシュテーブルが使われる。新しいファイルを開始するときにも動作
するように、カウントは接辞ファイルの COMMON 項目に列挙された単語で初期化され
る。

Vim が長く実行されるほどカウントが大きくなるので、これは理想的ではない。しかし
実際には、単語のカウントを使わないことに比べて、目に見える改善になっている。

3. 前提                                                 design-assumptions

以下のセクションは、すべての Vim のコードとビルドツールが従わなければならない、
移植性と互換性の制約を定義する。


Makefile                                       assumptions-makefiles
                                                POSIX.1-2001

Vim のメインの Makefile は最大限の移植性を目指しており、POSIX.1-2001 の make
で定義された機能のみに依存し、それ以降の POSIX 標準や GNU/BSD の拡張は無視して
いる。実際的には、以下を避ける:

        - % パターンルール
        - POSIX.1-2001 外のモダンな代入 (:=、::=)
        - 特殊ターゲット (.ONESHELL、.NOTPARALLEL、.SILENT、...)
        - 順序のみの前提条件 (|) や、ディレクトリの自動作成
        - GNU/BSD の条件文 (ifdef、ifndef、.for/.endfor、...)

POSIX.1-2001 は従来のサフィックスルールしかサポートしていないので、別のディレ
クトリでビルドされるすべてのオブジェクトには、明示的なルールがなければならな
い。例えば:

        objects/evalbuffer.o: evalbuffer.c
                $(CCC) -o $@ evalbuffer.c

この冗長さにより、同じ Makefile で、Linux、*BSD、macOS、Solaris、AIX、HP-UX
と、事実上すべての Unix 系 OS のデフォルトの make で、Vim を変更なしにビルド
できることが保証される。

いくつかのプラットフォーム固有の Makefile (例えば、Windows、NSIS、Cygwin 用)
は、基本的な make との互換性が必要でない場合に、より高度な機能を使うことがあ
る。


C コンパイラ                                   assumptions-C-compiler
                                                ANSI-C C89 C90 C95 C99

Vim は最大限の移植性を目指しており (design-multi-platform を参照)、今でも
OpenVMS VAX V7.3 上の Compaq C V6.4-005 でビルドできなければならない。

そのため、私たちが従う最新の ISO C 標準は:

        C95 (ISO/IEC 9899:1990/AMD1:1995)

加えて、以下の C99 の機能は明示的に許可されている:
        - // コメント (style-comments で必須とされている);
        - ブロック内での宣言と文の混在;
        - 可変長引数マクロ (..., __VA_ARGS__);
        - enum リストの末尾のコンマ;
        - _Bool 型 (bool、true、false 用);
        - __func__ 定義済み識別子;
        - inline 関数 (移植性のために static inline を使う);
        - 複合リテラル (type){ initializer-list };
        - 4095 文字までの論理ソース行。

プラットフォーム固有のコードは、そのプラットフォームでサポートされている、より
新しいコンパイラの機能を使ってもよい。


変数のサイズ                                   assumptions-variables

型のサイズについては POSIX.1-2001 (SUSv3) に従う。これは実際には以下を意味する:

        char_u      8-bit unsigned
        int         32-bit 以上の signed
        unsigned    32-bit 以上の unsigned


関数プロトタイプ                               assumptions-prototypes

Vim は、ほとんどの内部関数のプロトタイプに、従来のヘッダファイル (.h) を使わ
ない。代わりに、現在のアーキテクチャでは、src/proto/ ディレクトリにある個別
の .pro ファイルを、.c ファイルごとに 1 つの .pro ファイルで使う。

従来の自己完結したヘッダファイルとは異なり、これらの .pro ファイルには、API
のドキュメント、構造体と列挙型の定義、その他の宣言は含まれておらず、関数プロト
タイプだけが含まれている。

src/Makefile の make proto ターゲットは、python3-clang モジュールに依存す
る Python スクリプト proto/gen_prototypes.py を使って、ほとんどの .pro ファイ
ルの更新を自動化する。Note いくつかの proto ファイルは手で編集されていることに
注意。

4. コーディングスタイル                                 coding-style

これらは、Vim のソースコードに変更を加えるときに使うルールである。ソースを読み
やすく保守しやすく保つために、これらのルールを守ってほしい。

このリストは完全ではない。さらなる例については、ソースコードを見ること。

コードリポジトリには editorconfig ファイルが含まれており、配布されている
editorconfig プラグイン editorconfig-install と一緒に使うことで、推奨される
スタイルに従うことを保証できる。


変更を加える                                           style-changes

コードに変更を加える基本的な手順:
1. github からコードを入手する。そうすると、変更したバージョンをメインのコード
   ベースと同期させておくのが簡単になる (変更が取り込まれるまでには、しばらく
   かかるかもしれない)。
2. ドキュメントを調整する。これを最初に行うことで、変更がユーザーにどう影響す
   るかの印象がつかめる。
3. ソースコードの変更を行う。
4. 変更が列挙されている項目に影響するかどうか、../doc/todo.txt を確かめる。
5. 新しい動作を検証し、将来それが退行しないことを保証するために、src/testdir
   にテストを追加する。
6. "git diff" でパッチを作る。
7. 何が変わったかについてのメモを書く。できれば、問題と解決策に触れる。説明を
   付けて vim-dev メーリングリストにメールを送り、diff を含める。

些細でない変更については、テストスイートが実行されるので、常に github でプルリ
クエストを作ってほしい。

PR は、理想的には 1 つの論理的な変更に対して 1 つのコミットを含むべきである。
ただし、複数の論理的でアトミックな変更を 1 つの PR にまとめたい場合は、複数の
コミットを含めることができる。これにより、長い PR のレビューもしやすくなる。レ
ビューの過程に大いに役立つので、各コミットメッセージで変更の理由を必ず説明する
こと。各コミットが異なる論理的な変更を扱っている場合は、それらは Vim のリポジ
トリに別々のパッチとしても適用される。

                                                        style-clang-format
sound.c と sign.c は、配布されている .clang-format ファイルに従って、
clang-format フォーマッタを使って (半) 自動的に整形できる。その他のソースファ
イルは、まだ .clang-format ファイルに対応していない。これは将来変わるかもしれ
ず、それらも整形し直されるかもしれない。


コメント                                               style-comments

関数の本体の中に複数行のコメントを入れることは避けるようにする: 関数の一部に
別々にコメントを付ける必要があるほど関数が複雑な場合、おそらく関数の構造を考え
直すべきである。

ファイルのヘッダと関数の説明にはこれを使う:
    /*
     * 説明
     */

その他のすべてにはこれを使う:
    // コメント


インデント                                             style-indentation

コードのインデントには 4 つのスペースを使う。Vim を使ってソースを編集している
場合、modeline のおかげで何もする必要はない。

他のエディタ用には、リポジトリのルートに .editorconfig が用意されている。

ソースファイル sign.c と sound.c、およびすべての新しいファイルでは、タブを
使わず、スペースだけを使う。加えて、すべての新しいファイルは、インデントのテス
トに通るように、set et を含むモードラインを含めなければならない。


宣言                                                   style-declarations

可能な場合は、for ループの変数をガードの中で宣言する:
OK:
    for (int i = 0; i < len; ++i)

間違い:
    int i;
    for (i = 0; i < len; ++i)

変数は常にデフォルト値付きで宣言する:
OK:
    int n = 0;
    int *ptr = NULL;

間違い:
    int n;
    int *ptr;


波括弧                                         style-braces

すべての波括弧は改行して新しい行に置かなければならない:
OK:
    if (cond)
    {
        cmd;
        cmd;
    }
    else
    {
        cmd;
        cmd;
    }

間違い:
    if (cond) {
        cmd;
        cmd;
    } else {
        cmd;
        cmd;
    }

OK:
    while (cond)
    {
        cmd;
        cmd;
    }

間違い:
    while (cond) {
        cmd;
        cmd;
    }

OK:
    do
    {
        cmd;
        cmd;
    } while (cond);

または
    do
    {
        cmd;
        cmd;
    }
    while (cond);

間違い:
    do {
        cmd;
        cmd;
    } while (cond);


型                                                         style-types

説明的な型を使う。これらは src/vim.h、src/structs.h などで定義されている。Note
すべてのカスタム型は "_T" で終わっていることに注意

例:
    linenr_T
    buf_T
    pos_T


空白と句読点                                              style-spaces

関数名と括弧の間には空白を入れない:

OK:     func(arg);
間違い: func (arg);

if、while、switch などの後には空白を入れる。

OK:     if (arg)        for (;;)
間違い: if(arg)         for(;;)

コンマまたはセミコロンの後には空白を入れる:

OK:     func(arg1, arg2);       for (i = 0; i < 2; ++i)
間違い: func(arg1,arg2);        for (i = 0;i < 2;++i)

'='、'+'、'/' などの前後には空白を入れる。

OK:     var = a * 5;
間違い: var=a*5;

似た動作をまとめるには、空行を使う。

OK:
    msg_puts_title(_("\n--- Signs ---"));
    msg_putchar('\n');

    if (rbuf == NULL)
        buf = firstbuf;
    else
        buf = rbuf;

    while (buf != NULL && !got_int)

間違い:
    msg_puts_title(_("\n--- Signs ---"));
    msg_putchar('\n');
    if (rbuf == NULL)
        buf = firstbuf;
    else
        buf = rbuf;
    while (buf != NULL && !got_int)


関数                                                   style-functions

戻り値の型を、別のインデントした行に書いた関数宣言を使う。

OK:
    int
    function_name(int arg1, int arg2)
    {
    }

間違い:
    int function_name(int arg1, int arg2)
    {
    }

その他                                         style-various

define された名前は大文字にするべきである:
    #define SOME_THING


機能は常に "FEAT_" で始める:
    #define FEAT_FOO


'\"' を使わないこと。扱えないコンパイラがある。'"' はうまく動作する。

これを使わないこと:
    #if HAVE_SOME

それを扱えず、"HAVE_SOME" が定義されていないと文句を言うコンパイラがある。
これを使う
    #ifdef HAVE_SOME

または
    #if defined(HAVE_SOME)


スタイル                                               style-examples

1 行に 1 つの文。

                a = 1;

間違い:     while (cond);

OK:         while (cond)
                ;

間違い:     do a = 1; while (cond);

OK:         do
                a = 1;
            while (cond);

5. ポリシー     design-policy new-features deprecated-features

新しいマイナーバージョン (例えば 9.2.0) またはメジャーバージョン (例えば 10.0)
がリリースされる間の時間は、開発サイクルと呼ばれる。開発サイクルの中では、C の
コアへの 1 つ 1 つの変更が、個々のパッチリリースを参照するために、新しく増やさ
れた人間が読めるパッチ番号を受け取る。典型的な開発リリースサイクルは数年続くこ
ともあり、約 1500 - 2500 のパッチ番号が積み重なる。

リリースが行われる前に、安定化期間が告知される。この期間中は、明らかなバグ修
正、セキュリティ修正、ドキュメントの変更、翻訳の更新、ランタイムファイルの更新
のみが受け入れられ (後方互換性のない変更を導入しない場合に限る)、次のリリース
の仕上げに集中する。

新しい機能は開発サイクルの中でのみ受け入れられ、安定化期間の中では受け入れられ
ない。サイクルの間は、新しい機能を開発することができ、変更することも許される
が、サイクルが閉じる前に確定させなければならない。

マイナーリリースが行われたら、そのリリースに含まれる機能は、後方互換性のない変
更を受けてはならない。後のパッチは、Vim の C のコアについて互換性を保つことが
期待される。ランタイムファイルは、ランタイムファイルのメンテナーに古い動作を変
える機会を与えるために、少し柔軟に扱われる。

開発サイクルの中で、機能が非推奨とマークされることがある。非推奨の機能は、適切
なスイッチによってコンパイル時に無効にできる。新しいリリースの後、非推奨の機能
は、続くサイクルで完全に削除されることがある。
