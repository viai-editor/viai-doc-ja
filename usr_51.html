                              プラグインを作る


プラグインは、特定の種類のファイルに対する設定、構文ハイライト、および多くの他
のものを定義するために使うことができます。この章では、最も一般的な Vim プラグ
インの書き方を説明します。

51.1  一般的なプラグインを書く                        write-plugin

多くの人が使えるような方法で Vim script を書くことができます。これはプラグイン
と呼ばれます。Vim ユーザーは、あなたのスクリプトを自分のプラグインディレクトリ
に置いて、その機能をすぐに使うことができます add-plugin。

実際には、2 種類のプラグインがあります:

  グローバルプラグイン: すべての種類のファイル用。
ファイルタイププラグイン: 特定の種類のファイル専用。

このセクションでは、1 つ目の種類について説明します。ほとんどの項目は、ファイル
タイププラグインを書くことにも関係があります。ファイルタイププラグインに特有の
ことは、次のセクション write-filetype-plugin にあります。

ここでは、新しいプラグインを書くのに推奨される方法である Vim9 構文を使いま
す。ファイルが vim9script コマンドで始まるようにしてください。


名前

まず最初に、あなたのプラグインの名前を選ばなければなりません。プラグインが提供
する機能は、その名前から明らかであるべきです。そして、他の誰かが、同じ名前だが
異なることをするプラグインを書く可能性は低くあるべきです。

タイプミスを修正するスクリプトは、"typecorrect.vim" と呼ぶことができるでしょ
う。ここではそれを例として使います。

プラグインがすべての人のために機能するには、いくつかのガイドラインに従うべきで
す。これは段階を追って説明されます。完全な例のプラグインは最後にあります。


本体

プラグインの本体、実際の作業を行う行から始めましょう:

 12     iabbrev teh the
 13     iabbrev otehr other
 14     iabbrev wnat want
 15     iabbrev synchronisation
 16             \ synchronization

もちろん、実際のリストはずっと長くあるべきです。

行番号は、いくつかのことを説明するためだけに追加されています、それらをあなたの
プラグインファイルに入れないでください!


最初の行

  1     vim9script noclear

一番最初のコマンドとして vim9script を使う必要があります。一番よいのは、それ
を一番最初の行に置くことです。

私たちが書いているスクリプトには、2 回目に読み込まれたときに抜け出すための
finish コマンドがあります。スクリプト内で定義された項目が失われるのを避ける
ために、"noclear" 引数が使われます。これについての詳細は vim9-reload に。


ヘッダー

おそらく、あなたはプラグインに新しい修正を追加し、すぐにいくつかのバージョンが
散らばることになるでしょう。そして、このファイルを配布するとき、人々は、誰がこ
のすばらしいプラグインを書いたのか、およびどこに意見を送ることができるのかを知
りたがるでしょう。したがって、あなたのプラグインの先頭にヘッダーを置いてくださ
い:

  2     # タイプミスを修正するための Vim グローバルプラグイン
  3     # Last Change:  2021 Dec 30
  4     # Maintainer:   Bram Moolenaar <Bram@vim.org>

著作権およびライセンスについて: プラグインはとても便利で、その配布を制限する価
値はほとんどないので、あなたのプラグインをパブリックドメインにするか、または
Vim の license を使うことを検討してください。プラグインの先頭近くの、これに
ついての短い注記で十分なはずです。例:

  5     # License:      このファイルはパブリックドメインに置かれている。


読み込まない

ユーザーがこのプラグインを常に読み込みたいとは限らない可能性があります。また
は、システム管理者がそれをシステム全体のプラグインディレクトリに置いたが、ユー
ザーは使いたい自分自身のプラグインを持っています。その場合、ユーザーはこの特定
のプラグインの読み込みを無効にする機会を持たなければなりません。これらの行がそ
れを可能にします:

  7     if exists("g:loaded_typecorrect")
  8       finish
  9     endif
 10     g:loaded_typecorrect = 1

これはまた、スクリプトが 2 回読み込まれたときに、無意味に関数を再定義し、2 回
追加される自動コマンドに対して問題を引き起こすことも避けます。

名前は "g:loaded_" で始め、その後にプラグインのファイル名をそのまま続けること
が推奨されます。"g:" は、他の場所がその機能が使用可能かどうかをチェックできる
ように、変数をグローバルにするために前に付けられます。"g:" なしでは、それはス
クリプトにローカルになるでしょう。

finish を使うと、Vim はファイルの残りを読むのをやめます、Vim は endif を見
つけるためにやはりコマンドを解析する必要があるので、ファイル全体の周りに
if-endif を使うよりもずっと速いです。


マッピング

では、プラグインをもっと面白くしましょう: カーソルの下の単語に対する修正を追加
するマッピングを追加します。このマッピングのために単にキーシーケンスを選ぶこと
もできますが、ユーザーがすでにそれを何か他のことに使っているかもしれません。プ
ラグイン内のマッピングがどのキーを使うかをユーザーが定義できるようにするため
に、<Leader> 項目を使うことができます:

 20       map <unique> <Leader>a  <Plug>(TypecorrAdd)

"<Plug>(TypecorrAdd)" というものが作業を行います、それについての詳細は後で。

ユーザーは "g:mapleader" 変数を、プラグインのマッピングを始めたいキーシーケン
スに設定できます。したがって、ユーザーが以下を行っていた場合:

        g:mapleader = "_"

マッピングは "_a" を定義します。ユーザーがこれを行わなかった場合、バックスラッ
シュである既定値が使われます。その場合、"\a" に対するマップが定義されます。

Note <unique> が使われていることに注意、これは、マッピングがたまたますでに存在
していた場合、エラーメッセージを発生させます。:map-<unique>

しかし、ユーザーが自分自身のキーシーケンスを定義したい場合はどうでしょう? この
仕組みでそれを許可できます:

 19     if !hasmapto('<Plug>(TypecorrAdd)')
 20       map <unique> <Leader>a  <Plug>(TypecorrAdd)
 21     endif

これは "<Plug>(TypecorrAdd)" へのマッピングがすでに存在するかどうかをチェック
し、存在しない場合だけ "<Leader>a" からのマッピングを定義します。その場合、ユー
ザーには、これを自分の vimrc ファイルに入れる機会があります:

        map ,c  <Plug>(TypecorrAdd)

その場合、マップされたキーシーケンスは "_a" または "\a" の代わりに ",c" になり
ます。


部品

スクリプトが長くなると、作業を部品に分割したいことがよくあります。これには関数
またはマッピングを使えます。しかし、これらの関数およびマッピングが他のスクリプ
トのものと干渉してほしくはありません。例えば、関数 Add() を定義できますが、別
のスクリプトが同じ関数を定義しようとするかもしれません。これを避けるために、関
数をスクリプトにローカルに定義します。幸い、Vim9 script ではこれが既定です。
旧来のスクリプトでは、名前の前に "s:" を付ける必要があるでしょう。

新しいタイプ修正を追加する関数を定義します:

 28     def Add(from: string, correct: bool)
 29       var to = input($"type the correction for {from}: ")
 30       exe $":iabbrev {from} {to}"
 ...
 34     enddef

これで、このスクリプトの中から関数 Add() を呼び出すことができます。別のスクリ
プトも Add() を定義している場合、それはそのスクリプトにローカルで、そのスクリ
プトからだけ呼び出すことができます。グローバルな g:Add() 関数も存在し得て、そ
れはまた別の関数です。

<SID> はマッピングで使うことができます。それは、カレントスクリプトを識別するス
クリプト ID を生成します。私たちのタイプ修正プラグインでは、これをこのように使
います:

 22     noremap <unique> <script> <Plug>(TypecorrAdd)  <SID>Add
 ...
 26     noremap <SID>Add  :call <SID>Add(expand("<cword>"), true)<CR>

したがって、ユーザーが "\a" をタイプすると、このシーケンスが呼び出されます:

        \a  ->  <Plug>(TypecorrAdd)  ->  <SID>Add  ->  :call <SID>Add(...)

別のスクリプトも <SID>Add をマップする場合、それは別のスクリプト ID を得て、し
たがって別のマッピングを定義します。

Note ここでは Add() の代わりに <SID>Add() を使っていることに注意。それは、マッ
ピングはユーザーによってタイプされ、したがってスクリプトのコンテキストの外にあ
るからです。Vim がどのスクリプトで Add() 関数を探せばよいかが分かるように、
<SID> はスクリプト ID に変換されます。

これは少し複雑ですが、プラグインが他のプラグインと一緒に機能するために必要で
す。基本的なルールは、マッピングでは <SID>Add() を使い、他の場所 (スクリプト自
体、自動コマンド、ユーザーコマンド) では Add() を使うということです。

マッピングと同じことを行うメニュー項目を追加することもできます:

 24     noremenu <script> Plugin.Add\ Correction      <SID>Add

"Plugin" メニューは、プラグイン用のメニュー項目を追加するために推奨されていま
す。この場合、1 つの項目だけが使われています。より多くの項目を追加するときは、
サブメニューを作成することが推奨されます。例えば、"Plugin.CVS" は、CVS 操作
"Plugin.CVS.checkin"、"Plugin.CVS.checkout" などを提供するプラグインに使うこと
ができるでしょう。

Note 26 行目では、他のマッピングが問題を起こすのを避けるために ":noremap" が使
われていることに注意。例えば、誰かが ":call" を再マップしているかもしれません。
22 行目でも ":noremap" を使っていますが、"<SID>Add" は再マップされてほしいので
す。これが、ここで "<script>" が使われている理由です。これは、スクリプトにロー
カルなマッピングだけを許可します。:map-<script>  24 行目でも ":noremenu" に
対して同じことが行われています。:menu-<script>


<SID> と <Plug>                                        using-<Plug>

<SID> および <Plug> は両方とも、タイプされたキーのマッピングが、他のマッピング
からだけ使われるべきマッピングと干渉するのを避けるために使われます。<SID> を使
うことと <Plug> を使うことの間の違いに注意してください:

<Plug>  スクリプトの外から見えます。これは、ユーザーがキーシーケンスをマップし
        たいと思うかもしれないマッピングに使われます。<Plug> は、タイプされた
        キーが決して生成しない特殊なコードです。
        他のプラグインが同じ文字のシーケンスを使う可能性を非常に低くするため
        に、この構造を使ってください: <Plug> scriptname mapname 私たちの例で
        は、scriptname は "Typecorr" で、mapname は "Add" です。名前を括弧で囲
        みます。これにより "<Plug>(TypecorrAdd)" になります。PascalCase を使う
        慣習は、scriptname を mapname と区別するのに役立ちます。

        Note: "<Plug>" の後のテキストはプラグインの作者によって選ばれ、完全に
        任意です。名前を括弧で囲むこと、PascalCase を使うこと、または
        "<Plug>TypecorrAdd;" のような ";" 終端子を追加することは、名前を読みや
        すく、かつ他のプラグインと衝突しにくく保つための慣習にすぎません。それ
        らのどれも必須ではありません: 重要なのは、シーケンスが "<Plug>" で始ま
        り、一意であることだけです。
        {lhs} が <Plug> で始まるマッピングは、再マップが明示的に禁止されている
        場合でも、常に別のマッピングの {rhs} に適用されます。:nore

<SID>   スクリプト ID、スクリプトに対する一意な識別子です。
        内部的に、Vim は <SID> を、"123" が任意の数であり得る "<SNR>123_" に変
        換します。したがって、関数 "<SID>Add()" は、あるスクリプトでは
        "<SNR>11_Add()" という名前を持ち、別のスクリプトでは "<SNR>22_Add()"
        という名前を持ちます。関数のリストを得るために ":function" コマンドを
        使う場合、これを見ることができます。マッピング内の <SID> の変換はまっ
        たく同じです、それが、マッピングからスクリプトローカルな関数を呼び出せ
        る仕組みです。
        Note: <SID> がマッピングの {rhs} に現れるときは、<script> を使うことを
        検討してもよいでしょう。:map-<script>


ユーザーコマンド

では、修正を追加するユーザーコマンドを追加しましょう:

 36     if !exists(":Correct")
 37       command -nargs=1  Correct  :call Add(<q-args>, false)
 38     endif

同じ名前のコマンドがまだ存在しない場合だけ、ユーザーコマンドが定義されます。さ
もないと、ここでエラーが発生するでしょう。既存のユーザーコマンドを ":command!"
で上書きするのはよい考えではありません、これはおそらく、ユーザーに、自分自身で
定義したコマンドがなぜ機能しないのかと不思議に思わせるでしょう。:command そ
れが起こった場合、以下で誰のせいかを突き止めることができます:

        verbose command Correct


スクリプト変数

変数が "s:" で始まるとき、それはスクリプト変数です。それはスクリプトの中でだけ
使うことができます。スクリプトの外では、それは見えません。これにより、異なるス
クリプトで同じ変数名を使うことによる問題が避けられます。変数は Vim が実行され
ている間保持されます。そして、同じスクリプトを再び読み込むときに、同じ変数が使
われます。s:var

Vim9 script の良いところは、変数が既定でスクリプトにローカルであることです。
望む場合、"s:" を前に付けることもできますが、その必要はありません。そして、ス
クリプト内の関数も、プリフィックスなしでスクリプト変数を使うことができます (こ
れが機能するには、それらは関数の前に宣言されていなければなりません)。

スクリプトローカル変数は、スクリプト内で定義された関数、自動コマンド、および
ユーザーコマンドでも使うことができます。したがって、それらは、それが外に漏れる
ことなく、あなたのプラグインの部分の間で情報を共有するための完璧な方法です。私
たちの例では、修正の数を数えるための数行を追加できます:

 17     var count = 4
 ...
 28     def Add(from: string, correct: bool)
 ...
 32       count += 1
 33       echo "you now have " .. count .. " corrections"
 34     enddef

"count" はスクリプト自体の中で宣言され、4 に初期化されます。後で Add() 関数が
呼ばれると、それは "count" をインクリメントします。関数がどこから呼ばれたかは
問題ではありません、それはスクリプト内で定義されているので、このスクリプトの
ローカル変数を使います。


結果

これが、結果として得られる完全な例です:

  1     vim9script noclear
  2     # タイプミスを修正するための Vim グローバルプラグイン
  3     # Last Change:  2021 Dec 30
  4     # Maintainer:   Bram Moolenaar <Bram@vim.org>
  5     # License:      このファイルはパブリックドメインに置かれている。
  6
  7     if exists("g:loaded_typecorrect")
  8       finish
  9     endif
 10     g:loaded_typecorrect = 1
 11
 12     iabbrev teh the
 13     iabbrev otehr other
 14     iabbrev wnat want
 15     iabbrev synchronisation
 16             \ synchronization
 17     var count = 4
 18
 19     if !hasmapto('<Plug>(TypecorrAdd)')
 20       map <unique> <Leader>a  <Plug>(TypecorrAdd)
 21     endif
 22     noremap <unique> <script> <Plug>(TypecorrAdd)  <SID>Add
 23
 24     noremenu <script> Plugin.Add\ Correction      <SID>Add
 25
 26     noremap <SID>Add  :call <SID>Add(expand("<cword>"), true)<CR>
 27
 28     def Add(from: string, correct: bool)
 29       var to = input($"type the correction for {from}: ")
 30       exe $":iabbrev {from} {to}"
 31       if correct | exe "normal viws\<C-R>\" \b\e" | endif
 32       count += 1
 33       echo "you now have " .. count .. " corrections"
 34     enddef
 35
 36     if !exists(":Correct")
 37       command -nargs=1  Correct  call Add(<q-args>, false)
 38     endif

31 行目はまだ説明していませんでした。それは新しい修正をカーソルの下の単語に適
用します。新しい短縮入力を使うために :normal コマンドが使われます。Note 関数
が ":noremap" で定義されたマッピングから呼ばれたにもかかわらず、ここではマッピ
ングおよび短縮入力が展開されることに注意。


ドキュメント                                           write-local-help

あなたのプラグインのドキュメントもいくらか書くのはよい考えです。特に、その動作
がユーザーによって変更できるときは。ヘルプファイルで使われる構文については
help-writing を、ローカルヘルプファイルがどのようにインストールされるかにつ
いては add-local-help を参照してください。

これは、"typecorrect.txt" と呼ばれる、プラグインのヘルプファイルの簡単な例です:


  1     *typecorrect.txt*       Plugin for correcting typing mistakes
  2
  3     If you make typing mistakes, this plugin will have them corrected
  4     automatically.
  5
  6     There are currently only a few corrections.  Add your own if you like.
  7
  8     Mappings:
  9     <Leader>a   or   <Plug>(TypecorrAdd)
 10             Add a correction for the word under the cursor.
 11
 12     Commands:
 13     :Correct {word}
 14             Add a correction for {word}.
 15
 16                                                     *typecorrect-settings*
 17     This plugin doesn't have any settings.

最初の行が、実際のところ書式が重要な唯一の行です。それはヘルプファイルから抽出
され、help.txt の "LOCAL ADDITIONS:" セクションに入れられます
local-additions。最初の "*" は最初の行の最初の桁になければなりません。あなた
のヘルプファイルを追加した後、":help" を実行して、項目がきれいに並んでいること
を確認してください。

あなたのヘルプファイルの中で、** の中にさらにタグを追加できます。しかし、既存
のヘルプタグを使わないように注意してください。おそらく、その例の
"typecorrect-settings" のように、ほとんどのタグにあなたのプラグインの名前を使
うことになるでしょう。

|| の中で、ヘルプの他の部分への参照を使うことが推奨されます。これにより、ユー
ザーが関連するヘルプを見つけやすくなります。


まとめ                                         plugin-special

プラグインで使う特別なもののまとめ:

var name                スクリプトにローカルな変数。

<SID>                   スクリプト ID、スクリプトにローカルなマッピングおよび
                        関数に使われる。

hasmapto()              スクリプトが提供する機能に対するマッピングを、ユーザー
                        がすでに定義しているかどうかをテストする関数。

<Leader>                ユーザーが、プラグインのマッピングが始まるキーとして定
                        義する "mapleader" の値。

map <unique>            マッピングがすでに存在する場合、警告を出す。

noremap <script>        このスクリプトで定義された、<SID> で始まるマッピングだ
                        けを再マップする。

exists(":Cmd")          ユーザーコマンドがすでに存在するかどうかをチェックす
                        る。

51.2  ファイルタイププラグインを書く  write-filetype-plugin ftplugin

ファイルタイププラグインはグローバルプラグインに似ていますが、カレントバッファ
に対してだけオプションを設定し、マッピングを定義する点が異なります。この種類の
プラグインがどのように使われるかについては、add-filetype-plugin を参照してく
ださい。

まず、上のグローバルプラグインについてのセクション 51.1 を読んでください。そ
こで述べられていることはすべて、ファイルタイププラグインにも当てはまります。い
くつかの追加事項があり、それらはここで説明します。本質的なことは、ファイルタイ
ププラグインはカレントバッファにだけ効果を持つべきだということです。


無効化

多くの人に使われるファイルタイププラグインを書いている場合、彼らにはその読み込
みを無効にする機会が必要です。プラグインの先頭にこれを置いてください:

        # このバッファに対してまだ行われていないときだけ、これを行う
        if exists("b:did_ftplugin")
          finish
        endif
        b:did_ftplugin = 1

これは、同じプラグインが同じバッファに対して 2 回実行されるのを避けるためにも
使われる必要があります (引数なしで ":edit" コマンドを使うときに起こります)。

これで、ユーザーは、これらの行だけを持つファイルタイププラグインを作ることで、
既定のプラグインの読み込みを完全に無効にできます:

        vim9script
        b:did_ftplugin = 1

これには、ファイルタイププラグインディレクトリが 'runtimepath' で $VIMRUNTIME
より前に来ることが必要です!

既定のプラグインを使いたいが、設定の 1 つを上書きしたい場合、異なる設定をスク
リプトに書くことができます:

        setlocal textwidth=70

では、配布されている "vim.vim" ftplugin after-directory の後に読み込まれるよ
うに、これを "after" ディレクトリに書いてください。Unix では、これは
"~/.vim/after/ftplugin/vim.vim" になるでしょう。Note 既定のプラグインは
"b:did_ftplugin" を設定しているでしょう、それはここでは無視されることに注意。


オプション

ファイルタイププラグインがカレントバッファにだけ影響することを確実にするには、
オプションを設定するのに

        setlocal

コマンドを使ってください。そして、バッファにローカルなオプションだけを設定して
ください (それを確認するには、そのオプションのヘルプを参照してください)。グロー
バルオプション、またはウィンドウにローカルなオプションに対して :setlocal を
使うと、値は多くのバッファで変わり、それはファイルタイププラグインがすべきこと
ではありません。

オプションがフラグまたは項目のリストである値を持つとき、既存の値を保持するため
に "+=" および "-=" を使うことを検討してください。ユーザーがすでにオプションの
値を変更しているかもしれないことに注意してください。最初に既定値にリセットして
から変更するのは、多くの場合よい考えです。例:

        setlocal formatoptions& formatoptions+=ro


マッピング

マッピングがカレントバッファでだけ機能することを確実にするには

        map <buffer>

コマンドを使ってください。これは、上で説明した 2 段階のマッピングと組み合わせ
る必要があります。ファイルタイププラグインで機能を定義する方法の例:

        if !hasmapto('<Plug>JavaImport;')
          map <buffer> <unique> <LocalLeader>i <Plug>JavaImport;
        endif
        noremap <buffer> <unique> <Plug>JavaImport; oimport ""<Left><Esc>

hasmapto() は、ユーザーがすでに <Plug>JavaImport; へのマップを定義しているか
どうかをチェックするために使われます。そうでない場合、ファイルタイププラグイン
は既定のマッピングを定義します。これは <LocalLeader> で始まり、それは、ユー
ザーがファイルタイププラグインのマッピングを始めたいキーを選択できるようにしま
す。既定はバックスラッシュです。
"<unique>" は、マッピングがすでに存在するか、または既存のマッピングと重なる場
合に、エラーメッセージを出すために使われます。
:noremap は、ユーザーが定義した他のマッピングが干渉するのを避けるために使わ
れます。<SID> で始まる、このスクリプトで定義されたマッピングの再マップを許可す
るために、":noremap <script>" を使いたいかもしれません。

ユーザーは、すべてを無効にすることなく、ファイルタイププラグインのマッピングを
無効にする機会を持たなければなりません。ここに、mail ファイルタイプ用のプラグ
インに対してこれがどのように行われるかの例があります:

        # マッピングを追加する、ただしユーザーがこれを望まなかった場合は除く。
        if !exists("g:no_plugin_maps") && !exists("g:no_mail_maps")
          # "> " を挿入してテキストを引用する
          if !hasmapto('<Plug>MailQuote;')
            vmap <buffer> <LocalLeader>q <Plug>MailQuote;
            nmap <buffer> <LocalLeader>q <Plug>MailQuote;
          endif
          vnoremap <buffer> <Plug>MailQuote; :s/^/> /<CR>
          nnoremap <buffer> <Plug>MailQuote; :.,$s/^/> /<CR>
        endif

2 つのグローバル変数が使われています:
g:no_plugin_maps      すべてのファイルタイププラグインに対するマッピングを無効にする
g:no_mail_maps        "mail" ファイルタイプに対するマッピングを無効にする


ユーザーコマンド

特定のファイルタイプに対して、1 つのバッファでだけ使えるようにユーザーコマンド
を追加するには、:command に "-buffer" 引数を使ってください。例:

        command -buffer  Make  make %:r.s


変数

ファイルタイププラグインは、それが対象とするタイプの各バッファに対して読み込ま
れます。ローカルなスクリプト変数は、すべての呼び出しの間で共有されます。特定の
1 つのバッファ用の変数が欲しい場合、ローカルなバッファ変数 b:var を使ってく
ださい。


関数

関数を定義するとき、これは 1 回だけ行えば済みます。しかし、ファイルタイププラ
グインは、このファイルタイプのファイルが開かれるたびに読み込まれます。この構造
は、関数が 1 回だけ定義されることを確実にします:

        if !exists("*Func")
          def Func(arg)
            ...
          enddef
        endif

スクリプトが 2 回目に読み込まれたときに関数が削除されるのを避けるために、
vim9script コマンドで "noclear" を使うことを忘れないでください。


UNDO                                            undo_indent undo_ftplugin

ユーザーが ":setfiletype xyz" を行ったとき、前のファイルタイプの効果は undo さ
れるべきです。b:undo_ftplugin 変数に、あなたのファイルタイププラグインの設定を
undo するコマンドを設定してください。例:

        b:undo_ftplugin = "setlocal fo< com< tw< commentstring<"
                \ .. "| unlet b:match_ignorecase b:match_words b:match_skip"

":setlocal" をオプション名の後の "<" とともに使うと、オプションはそのグローバ
ル値にリセットされます。たいていは、それがオプションの値をリセットする最良の方
法です。

インデントスクリプトの効果を undo するためには、b:undo_indent 変数をそれに応じ
て設定する必要があります。

これらの変数はどちらも、Vim9 構文ではなく、旧来のスクリプト構文を使います。

推奨スタイル                                   ft_recommended_style

ファイルタイププラグインまたはインデントスクリプトは、言語の厳格な要件ではな
く、そのファイルタイプの推奨される、または一般的に使われるスタイルを反映するオ
プションを設定することがあります。すべてのユーザーがこれらのスタイル上の設定を
望むわけではないので、それらを無効にできるようにガードしてください。

既定値を有効 (1) として、2 つの変数を、ファイルタイプ固有のものを最初に、次に
一般的なものをチェックしてください:

        if get(g:, '<filetype>_recommended_style',
                \ get(g:, 'filetype_recommended_style', 1))
          " ここで推奨スタイルのオプションを設定する
        endif

filetype> を実際のファイルタイプ名に置き換えてください、例えば "python" では
g:python_recommended_style になります。

これにより、ユーザーはすべてのファイルタイプに対して推奨スタイル設定をオフにで
きます:

        let g:filetype_recommended_style = 0

または、残りを有効のままにして、1 つのファイルタイプに対して:

        let g:python_recommended_style = 0

ファイルタイプ固有の変数は一般的な変数よりも優先されるので、ユーザーは
g:filetype_recommended_style ですべての場所でスタイル設定を無効にし、
g:<filetype>_recommended_style を 1 に設定することで単一のファイルタイプに対し
て再び有効にすることができます (またはその逆)。

言語が正しく機能するために必要な設定 (単にスタイル上のものではない) は、この
ガードの後ろに置くべきではありません。

ファイル名

ファイルタイプはファイル名に含まれていなければなりません ftplugin-name。これ
らの 3 つの形式のうちの 1 つを使ってください:

        .../ftplugin/stuff.vim
        .../ftplugin/stuff_foo.vim
        .../ftplugin/stuff/bar.vim

"stuff" はファイルタイプで、"foo" および "bar" は任意の名前です。


ファイルタイプ検出                                     plugin-filetype

あなたのファイルタイプがまだ Vim によって検出されない場合、ファイルタイプ検出
のスニペットを別のファイルに作成するべきです。それは通常、ファイル名がパターン
にマッチするときにファイルタイプを設定する自動コマンドの形式です。例:

        au BufNewFile,BufRead *.foo             setlocal filetype=foofoo

この 1 行のファイルを、'runtimepath' に現れる最初のディレクトリに
"ftdetect/foofoo.vim" として書いてください。Unix では、それは
"~/.vim/ftdetect/foofoo.vim" になるでしょう。慣習は、スクリプト名にファイルタ
イプの名前を使うことです。

望む場合、例えば言語を認識するためにファイルの内容を調べるために、より複雑な
チェックを行うことができます。new-filetype も参照してください。


まとめ                                         ftplugin-special

ファイルタイププラグインで使う特別なもののまとめ:

<LocalLeader>           ユーザーが、ファイルタイププラグインのマッピングが始ま
                        るキーとして定義する "maplocalleader" の値。

map <buffer>            バッファにローカルなマッピングを定義する。

noremap <script>        このスクリプトで定義された、<SID> で始まるマッピングだ
                        けを再マップする。

setlocal                カレントバッファに対してだけオプションを設定する。

command -buffer         バッファにローカルなユーザーコマンドを定義する。

exists("*s:Func")       関数がすでに定義されているかどうかをチェックする。

すべてのプラグインで使われる特別なものである plugin-special も参照してくださ
い。

51.3  コンパイラプラグインを書く              write-compiler-plugin

コンパイラプラグインは、特定のコンパイラで使うためのオプションを設定します。
ユーザーは :compiler コマンドでそれを読み込むことができます。主な用途は、
'errorformat' および 'makeprg' オプションを設定することです。

一番簡単なのは、例を見てみることです。このコマンドは、すべての既定のコンパイラ
プラグインを編集します:

        next $VIMRUNTIME/compiler/*.vim

次のプラグインファイルに行くには :next とタイプしてください。

これらのファイルには 2 つの特別な項目があります。1 つ目は、ユーザーが既定のファ
イルを上書きするか、または既定のファイルに追加することを可能にする仕組みです。
既定のファイルは以下で始まります:

        vim9script
        if exists("g:current_compiler")
          finish
        endif
        g:current_compiler = "mine"

コンパイラファイルを書いて、それをあなたの個人用のランタイムディレクトリ (例え
ば、Unix では ~/.vim/compiler) に置くとき、既定のファイルが設定をスキップする
ように "current_compiler" 変数を設定します。
                                                        :CompilerSet
2 つ目の仕組みは、":compiler!" に対しては ":set" を、":compiler" に対しては
":setlocal" を使うことです。Vim はこのために ":CompilerSet" ユーザーコマンドを
定義しています。これは例です:

  CompilerSet errorformat&              " 既定の 'errorformat' を使う
  CompilerSet makeprg=nmake

Note: 引数は option-backslash に従ってエスケープする必要があります。

Vim の配布物用、またはシステム全体のランタイムディレクトリ用のコンパイラプラグ
インを書くときは、上で述べた仕組みを使ってください。"current_compiler" がユー
ザープラグインによってすでに設定されていたときは、何も行われません。

既定のプラグインからの設定を上書きするためのコンパイラプラグインを書くときは、
"current_compiler" をチェックしないでください。このプラグインは最後に読み込ま
れることになっているので、'runtimepath' の最後にあるディレクトリにあるべきで
す。Unix では、それは ~/.vim/after/compiler になり得ます。

51.4  Vim script を配布する                           distribute-script

Vim ユーザーは Vim のウェブサイトでスクリプトを探すでしょう:
http://www.vim.org。
他の人に役立つものを作った場合、それを共有してください!

もう 1 つの場所は github です。しかし、そこではそれをどこで見つけるかを知って
いる必要があります! 利点は、ほとんどのプラグインマネージャーが github からプラ
グインを取得することです。それらを見つけるには、あなたのお気に入りの検索エンジ
ンを使う必要があるでしょう。

Vim script はどのシステムでも使えます。しかし、tar または gzip コマンドがない
かもしれません。ファイルをまとめる、および/または圧縮したい場合、"zip" ユーティ
リティが推奨されます。

最大限の移植性のためには、Vim 自体を使ってスクリプトをまとめてください。これは
Vimball ユーティリティで行うことができます。vimball を参照してください。

自動更新を可能にする行を追加するとよいです。glvs-plugins を参照してください。
