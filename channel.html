1. 概要                                                 job-channel-overview

ジョブには 4 つの主な種類がある:
1. 複数の Vim インスタンスに応えるデーモン。
   Vim はソケットでそれに接続する。
2. 1 つの Vim インスタンスと共に非同期に働く 1 つのジョブ。
   ソケットまたはパイプを使う。
3. 短時間、非同期に何らかの作業を行うジョブ。
   ソケットまたはパイプを使う。
4. 同期的にフィルタを実行する。
   パイプを使う。

ソケットを使う場合については job-start、job-start-nochannel および
channel-open を参照。2 および 3、パイプを使う 1 つ以上のジョブについては、
job-start を参照。4 については ":{range}!cmd" コマンドを使う、filter を参
照。

ソケットおよびパイプ上では、以下のプロトコルが使用可能:
RAW     何も分からない、Vim はメッセージがどこで終わるか判別できない
NL      全てのメッセージは NL (改行) 文字で終わる
JSON    JSON エンコーディング json_encode()
JS      JavaScript 風の JSON に似たエンコーディング js_encode()
LSP     Language Server Protocol エンコーディング language-server-protocol
DAP     Debug Adapter Protocol エンコーディング debug-adapter-protocol
MCP     Model Context Protocol エンコーディング model-context-protocol

よくある組み合わせは以下:
- NL モードでパイプを通して接続されたジョブを使う。例えば、スタイルチェッカー
  を実行し、エラーおよび警告を受け取るため。
- デーモンを使い、JSON モードでソケットを通して接続する。例えば、データベース
  で相互参照を調べるため。

2. チャネルデモ                         channel-demo demoserver.py

これには Python が必要。デモプログラムは $VIMRUNTIME/tools/demoserver.py にあ
る
それを 1 つの端末で実行する。これを T1 と呼ぶことにする。

別の端末で Vim を実行する。以下でデモサーバーに接続する:
        let channel = ch_open('localhost:8765')

T1 では以下が見えるはずだ:
        === socket opened ===

これでサーバーにメッセージを送信できる:
        echo ch_evalexpr(channel, 'hello!')

メッセージは T1 で受信され、応答が Vim に送り返される。
T1 で生のメッセージを見ることができる。Vim が送信するものは以下:
        [1,"hello!"]
そして応答は以下:
        [1,"got it"]
メッセージを送信するたびに番号が増える。

サーバーは Vim にコマンドを送信できる。T1 でこれを入力する (文字どおりに、引用
符を含めて):
        ["ex","echo 'hi there'"]
そして Vim にメッセージが表示されるはずだ。カーソルを 1 単語前方に移動できる:
        ["normal","w"]

非同期の通信を扱うには、コールバックを使う必要がある:
        func MyHandler(channel, msg)
          echo "from the handler: " .. a:msg
        endfunc
        call ch_sendexpr(channel, 'hello!', {'callback': "MyHandler"})
Vim は応答を待たない。これでサーバーは後で応答を送信でき、MyHandler が呼び出さ
れる。

送信の呼び出しごとにコールバックを与える代わりに、チャネルを開くときにそれを指
定することもできる:
        call ch_close(channel)
        let channel = ch_open('localhost:8765', {'callback': "MyHandler"})
        call ch_sendexpr(channel, 'hello channel!')

チャネルを試すときは、何が起きているかを見ると便利だ。Vim にログファイルに行を
書き込むよう指示できる:
        call ch_logfile('channellog', 'w')
ch_logfile() を参照。

ch_listen() を使って Vim をサーバーとして動作させることもできる。これは外部
のサーバープログラムを必要としない。

                                                        channel-listen-demo
Vim を開始し、待ち受けチャネルを作成する:
        func OnAccept(channel, clientaddr)
          " 接続をログに記録する
          echomsg "Accepted connection from " .. a:clientaddr

          " 現在時刻を取得し、それをクライアントに送信する
          let current_time = strftime("%Y-%m-%d %H:%M:%S")
          call ch_sendraw(a:channel, "Vim Server Time: " .. current_time .. "\n")

          " 任意: 時刻だけを提供したい場合、すぐに閉じる
          call ch_close(a:channel)
        endfunc

        " ポート 8765 で待ち受けを開始する
        let server = ch_listen('8765', {"callback": "OnAccept"})

別の Vim インスタンス (または任意のプログラム) から、それに接続できる:
        let channel = ch_open('localhost:8765')

終わったら、サーバーチャネルを閉じる:
        call ch_close(server)

                                                        channel-stdio
Vim は、エディタによって開始される言語サーバーのように、自身の stdin および
stdout 上でチャネルのもう一方の端になることもできる。--stdio-channel および
チャネルを開くスクリプトを付けて Vim を開始する:
        vim --stdio-channel -S server.vim
そして server.vim では:
        func OnMessage(ch, msg)
          ...
        endfunc
        let ch = ch_open('stdio', #{mode: 'lsp', callback: 'OnMessage'})

MCP サーバーには "lsp" の代わりに "mcp" モードを使う。model-context-protocol
を参照。
                                                        E1582 E1583
アドレス "stdio" は、Vim が --stdio-channel 付きで開始されたときにのみ、かつ
1 回だけ使用できる。そのとき Vim の stdin および stdout は null デバイスにリダ
イレクトされ、Vim から、および Vim が開始するコマンドからのメッセージがチャネ
ルに入らないようにする。stderr はそのままにされ、エラーメッセージに使用できる。

3. チャネルを開く                                       channel-open

チャネルを開くには:
    let channel = ch_open({address} [, {options}])
    if ch_status(channel) == "open"
      " チャネルを使う

チャネルを開けたかどうかを確認するには ch_status() を使う。

                                        channel-address
{address} は、ポート番号が後に続くドメイン名または IP アドレス、"unix:" が前に
付いた Unix ドメインソケットのパス、または "stdio" にできる。例:
    www.example.com:80   " ドメイン + ポート
    127.0.0.1:1234       " IPv4 + ポート
    [2001:db8::1]:8765   " IPv6 + ポート
    unix:/tmp/my-socket  " Unix ドメインソケットのパス
    stdio                " Vim の stdin および stdout、|channel-stdio| を参照

ドメイン名が複数のアドレス (例えば、IPv6 および IPv4 の両方) に解決される場合、
Vim は各アドレスを順に試す。接続が遅いか、または到達できない場合、すぐに次のア
ドレスにフォールバックする。これは、ネットワーク上で IPv6 または IPv4 に到達で
きない場合に役立つ。

{options} は省略可能なエントリを持つ辞書である:         channel-open-options

"mode" は以下にできる:                                  channel-mode
        "json" - JSON を使う、以下を参照。最も便利な方法。デフォルト。
        "js"   - JS (JavaScript) エンコーディングを使う。JSON より効率的。
        "nl"   - NL 文字で終わるメッセージを使う
        "raw"  - 生のメッセージを使う
        "blob" - 生のメッセージを使い、コールバックデータを Blob として渡す
        "lsp"  - language server protocol エンコーディングを使う。
                 language-server-protocol を参照
        "dap"  - debug adapter protocol エンコーディングを使う。
                 debug-adapter-protocol を参照
        "mcp"  - model context protocol エンコーディングを使う。
                 model-context-protocol を参照
                                                channel-callback E921
"callback"      他の方法で処理されないメッセージ (例えば、ID が 0 の JSON メッ
                セージ) を受信したときに呼ばれる関数。それは 2 つの引数を受け
                取る: チャネルおよび受信したメッセージ。
                例:
        func Handle(channel, msg)
          echo 'Received: ' .. a:msg
        endfunc
        let channel = ch_open("localhost:8765", {"callback": "Handle"})

                "mode" が "json"、"js"、"lsp"、"dap" または "mcp" のいずれかの
                場合、"msg" 引数は受信したメッセージの本体で、Vim の型に変換さ
                れている。
                "mode" が "nl" の場合、"msg" 引数は NL を除いた 1 つのメッセー
                ジである。
                "mode" が "raw" の場合、"msg" 引数は文字列としてのメッセージ全
                体である。
                "mode" が "blob" の場合、"msg" 引数は Blob としてのメッセー
                ジ全体である。

                全てのコールバックについて: 引数および/または辞書に束縛するに
                は function() を使う。または、辞書を束縛するには
                "dict.function" の形式を使う。

                コールバックは "安全な" 時点、通常は Vim がユーザーの文字入力
                を待っているときにのみ呼ばれる。Vim はマルチスレッドを使わな
                い。

                                                        close_cb
"close_cb"      ch_close() を呼ぶ以外の方法でチャネルが閉じられたときに呼ばれ
                る関数。このように定義するべきである:
        func MyCloseHandler(channel)
                Vim はデータを扱うコールバックを close_cb を呼び出す前に呼び出
                すので、この関数が呼ばれたときには、それ以上のデータはコール
                バックに渡されない。しかし、コールバックが Vim にメッセージを
                確認させた場合、まだコールバック内にいる間に close_cb が呼び出
                されることがある。プラグインはこれを何とかして処理しなければな
                らない、これ以上データが来ないことを知るのは有用でありうる。
                読み込むメッセージがあるかどうか分からない場合、try/catch ブ
                ロックを使う:
                        try
                          let msg = ch_readraw(a:channel)
                        catch
                          let msg = 'no message'
                        endtry
                        try
                          let err = ch_readraw(a:channel, #{part: 'err'})
                        catch
                          let err = 'no error'
                        endtry
                                                        channel-drop
"drop"          いつメッセージを破棄するかを指定する:
                    "auto"      メッセージを処理するコールバックが無いとき。
                                これには "close_cb" も考慮される。
                    "never"     全てのメッセージが保持される。

                                                        channel-noblock
"noblock"       job-noblock と同じ効果。書き込みにのみ関係する。

                                                        waittime
"waittime"      接続が確立されるのを待つミリ秒単位の時間。負の数は永久に待つ。

                デフォルトは 0 で、待たない、これはローカルサーバーが既に実行
                されているはずの場合に便利だ。Unix では Vim は実際には 1 ミリ
                秒のタイムアウトを使う、それは多くのシステムで必要とされる。リ
                モートサーバーにはより大きな値を使う、例えば少なくとも 10 ミリ
                秒。
                                                        channel-timeout
"timeout"       ブロックするときに要求を待つ時間、例えば ch_evalexpr() を使う
                とき。ミリ秒単位。デフォルトは 2000 (2 秒)。

"mode" が "json" または "js" の場合、"callback" は省略可能である。省略された場
合、メッセージを受信できるのはメッセージを 1 つ送信した後だけである。

チャネルを開いた後でチャネルオプションを変更するには ch_setoptions() を使う。
引数は ch_open() に渡されるものと似ているが、"waittime" は与えられない、それ
はチャネルを開くときにのみ適用されるためである。

例えば、ハンドラを追加または変更できる:
    call ch_setoptions(channel, {'callback': callback})
"callback" が空 (0 または空文字列) の場合、ハンドラは削除される。

コールバックが呼び出された後、Vim は画面を更新し、カーソルを本来の位置に戻す。
したがって、コールバックは :redraw を行う必要は無いはずだ。

タイムアウトは変更できる:
    call ch_setoptions(channel, {'timeout': msec})

                                                          channel-close E906
チャネルを使い終えたら、このように切断する:
    call ch_close(channel)
ソケットが使われている場合、これはソケットを両方向とも閉じる。パイプが使われて
いる場合 (stdin/stdout/stderr)、それらは全て閉じられる。これは望むものではない
かもしれない! ジョブを job_stop() で停止するほうがよいかもしれない。
先読みしたものは全て破棄され、コールバックはもう呼び出されない。

Note チャネルは 3 つの段階で閉じられることに注意:
  - I/O が終了する、ログメッセージ: "Closing channel"。読み込むべきキューに入っ
    たメッセージ、または呼び出すべきコールバックがまだ存在しうる。
  - 先読みがクリアされる、ログメッセージ: "Clearing channel"。いくつかの変数は
    まだチャネルを参照しているかもしれない。
  - チャネルが解放される、ログメッセージ: "Freeing channel"。

チャネルを開けない場合、エラーメッセージが表示される。MS-Windows と Unix の間
には違いがある: Unix ではポートが存在しない場合、ch_open() はすぐに失敗する。
MS-Windows では "waittime" が適用される。
E898 E901 E902

チャネルの読み込みまたは書き込みでエラーが発生した場合、チャネルは閉じられる。
E630 E631

4. JSON または JS チャネルを使う                                channel-use

モードが JSON の場合、このように同期的にメッセージを送信できる:
    let response = ch_evalexpr(channel, {expr})
これは相手側からの応答を待つ。

モードが JS の場合、これは同じように動作するが、メッセージは JavaScript エン
コーディングを使う。違いについては js_encode() を参照。

応答を処理せずに、またはチャネルコールバックに応答を処理させて、メッセージを送
信するには:
    call ch_sendexpr(channel, {expr})

メッセージを送信し、特定の関数に応答を処理させるには、非同期に:
    call ch_sendexpr(channel, {expr}, {'callback': Handler})

Vim はメッセージ ID を使って応答を要求と照合する。応答を受信すると、コールバッ
クが呼び出される。同じ ID を持つそれ以降の応答は無視される。サーバーが複数の応
答を送り返す場合、それらを ID 0 で送信する必要がある、それらはチャネルコール
バックに渡される。

{expr} は JSON に変換され、配列で包まれる。{expr} が文字列 "hello" の場合に受
信側が受け取るメッセージの例:
        [12,"hello"]

送信される JSON の形式は以下:
    [{number},{expr}]

ここで {number} は毎回異なる。それは応答 (ある場合) の中で使わなければならない:

    [{number},{response}]

こうすることで、Vim はどの送信メッセージがどの受信メッセージに対応するかを知
り、正しいハンドラを呼ぶことができる。メッセージが順不同で届いたときも。

改行文字が JSON テキストを終端する。これは読み込んだテキストを分割するのに使用
できる。例えば、Python では:
        splitidx = read_text.find('\n')
        message = read_text[:splitidx]
        rest = read_text[splitidx + 1:]

送信側は常に有効な JSON を Vim に送信しなければならない。Vim は JSON を解析す
ることでメッセージの終わりを確認できる。終わりを受信した場合にのみメッセージを
受け付ける。メッセージの後の改行は省略可能である。

プロセスが最初にメッセージを受信せずに Vim にメッセージを送信したい場合、番号
0 を使わなければならない:
    [0,{response}]

そのときチャネルハンドラは、Vim の型に変換された {response} を受け取る。チャネ
ルにハンドラが無い場合、メッセージは破棄される。

JSON または JS チャネルで ch_sendraw() および ch_evalraw() を使うこともできる。
その場合、呼び出し側が正しいエンコードおよびデコードに完全に責任を持つ。

5. チャネルコマンド                                     channel-commands

JSON チャネルでは、プロセスは Vim 内部で処理されるコマンドを Vim に送信できる、
それはチャネルのハンドラを必要としない。

可能なコマンドは以下:                           E903 E904 E905
    ["redraw", {forced}]
    ["ex",     {Ex command}]
    ["normal", {Normal mode command}]
    ["expr",   {expression}, {number}]
    ["expr",   {expression}]
    ["call",   {func name}, {argument list}, {number}]
    ["call",   {func name}, {argument list}]

これら全てについて: これらのコマンドが何をするかに注意すること! ユーザーが行っ
ていることを簡単に妨げることがある。トラブルを避けるには、mode() を使ってエ
ディタが期待される状態にあることを確認する。例えば、コマンドとして実行されるの
ではなく、テキストとして挿入されなければならないキーを送信するには:
    ["ex","if mode() == 'i' | call feedkeys('ClassName') | endif"]

これらのコマンドでのエラーは、画面表示を乱さないように通常は報告されない。それ
らを見たい場合、'verbose' オプションを 3 以上に設定する。


コマンド "redraw"

その他のコマンドは明示的には画面を更新しないので、カーソルが動き回ることなく一
連のコマンドを送信できる。いくつかのコマンドの副作用として再描画が起こることが
ある。変更されたテキストを表示し、カーソルを本来の位置に表示するには、"redraw"
コマンドで終えなければならない。

引数は通常、空文字列である:
        ["redraw", ""]
最初に画面をクリアするには "force" を渡す:
        ["redraw", "force"]


コマンド "ex"

"ex" コマンドは任意の Ex コマンドとして実行される。完了またはエラーに対する応
答は無い。autoload スクリプト内の関数を使うことができる:
        ["ex","call myscript#MyFunc(arg)"]

"call feedkeys()" を使って任意のキーシーケンスを挿入することもできる。

エラーがあるとき、チャネルログが存在する場合はそこにメッセージが書き込まれ、
v:errmsg にそのエラーが設定される。


コマンド "normal"

"normal" コマンドは ":normal!" のように実行され、コマンドはマップされない。カー
ソル下の折り畳みを開く例:
        ["normal" "zO"]


応答ありのコマンド "expr"

"expr" コマンドは式の結果を得るために使用できる。例えば、カレントバッファの行
数を得るには:
        ["expr","line('$')", -2]

それは式の結果を送り返す:
        [-2, "last line"]
形式は以下:
        [{number}, {result}]

ここで {number} は要求の中にあったものと同じである。Vim が送信するメッセージと
の混同を避けるために負の数を使う。要求と応答を照合できるように、要求ごとに異な
る番号を使う。

{result} は評価の結果で、JSON エンコードされる。評価が失敗するか、または結果を
JSON にエンコードできない場合、それは文字列 "ERROR" である。


応答なしのコマンド "expr"

このコマンドは上記の "expr" に似ているが、応答を何も送り返さない。例:
        ["expr","setline('$', ['one', 'two', 'three'])"]
要求に 3 番目の引数は無い。


コマンド "call"

これは "expr" に似ているが、式全体を文字列として渡す代わりに、関数の名前および
引数のリストを渡す。これにより、引数を文字列に変換すること、およびそれらをエス
ケープして連結することが避けられる。例:
        ["call", "line", ["$"], -2]

応答を送信しない場合、4 番目の引数を省く:
        ["call", "setline", ["$", ["one", "two", "three"]]]

6. RAW または NL チャネルを使う                         channel-raw

モードが RAW または NL の場合、このようにメッセージを送信できる:
    let response = ch_evalraw(channel, {string})

{string} はそのまま送信される。応答はチャネルからすぐに読み込めるものになる。
Vim はメッセージの終わりを認識する方法を知らないので、それは自分で処理する必要
がある。タイムアウトは最初のバイトを読み込むことに適用され、その後はそれ以上何
も待たない。

モードが "nl" の場合、同様の方法でメッセージを送信できる。各メッセージの後に
NL を入れることが求められる。したがって、NL で終わる複数のメッセージを一度に送
信することもできる。応答は、最初の NL までの、それを含むテキストになる。空の応
答では、これは NL だけでもありうる。
チャネルタイムアウトまでに NL が読み込まれなかった場合、空文字列が返される。

応答を期待せずにメッセージを送信するには:
    call ch_sendraw(channel, {string})
プロセスは応答を送り返すことができ、チャネルハンドラがそれを引数にして呼ばれ
る。

                                                channel-onetime-callback
メッセージを送信し、特定の関数に応答を処理させるには、非同期に:
    call ch_sendraw(channel, {string}, {'callback': 'MyHandler'})

この {string} は JSON でもよく、それを作成するには json_encode() を、受信し
た JSON メッセージを処理するには json_decode() を使う。

raw チャネルでは ch_evalexpr() または ch_sendexpr() を使うことはできない。

Vim の文字列は NUL バイトを含むことができない。NUL バイトを送信または受信する
には、バッファから読み込むか、またはバッファに書き込む。in_io-buffer および
out_io-buffer を参照。

7. その他のチャネル関数                                 channel-more

チャネルの状態を得るには: ch_status(channel)。可能な結果は以下:
        "fail"          チャネルを開くのに失敗した。
        "open"          チャネルを使用できる。
        "buffered"      チャネルは閉じられたが、読み込むデータがある。
        "closed"        チャネルは閉じられた。

チャネルに関連付けられたジョブを得るには: ch_getjob(channel)

チャネルから 1 つのメッセージを読み込むには:
        let output = ch_read(channel)
これはチャネルタイムアウトを使う。タイムアウトなしで読み込む、つまり使用可能な
任意のメッセージを得るだけにするには:
        let output = ch_read(channel, {'timeout': 0})
使用可能なメッセージが無かった場合、結果は JSON または JS モードのチャネルでは
v:none、RAW または NL チャネルでは空文字列になる。読み込むものがあるかどうかを
確認するには ch_canread() を使用できる。

Note コールバックが無い場合、メッセージは破棄されることに注意。それを避けるに
は、チャネルに close コールバックを追加する。

RAW チャネルから使用可能な全ての通常出力を読み込むには:
        let output = ch_readraw(channel)
RAW チャネルから使用可能な全てのエラー出力を読み込むには:
        let output = ch_readraw(channel, {"part": "err"})
Note チャネルが NL モードの場合、ch_readraw() は呼び出しごとに 1 行しか返さな
いことに注意。

ch_read() および ch_readraw() はチャネルタイムアウトを使う。その時間内に読み込
むものが無い場合、空文字列が返される。異なるタイムアウトをミリ秒で指定するには
"timeout" オプションを使う:
        {"timeout": 123}
エラー出力から読み込むには "part" オプションを使う:
        {"part": "err"}
JS または JSON チャネルで、特定の ID を持つメッセージを読み込むには:
        {"id": 99}
ID が指定されていないか、または ID が -1 の場合、最初のメッセージが返される。
これは、このメッセージを待っているどのコールバックよりも優先される。

RAW チャネルでは、Vim はメッセージがどこで終わるか分からないので、これは使用可
能なものを何でも返す。
NL チャネルでは、これは 1 つのメッセージを返す。
JS または JSON チャネルでは、これは 1 つのデコードされたメッセージを返す。
これにはシーケンス番号も含まれる。

                戻り値の型: channel

                {handle} が渡された場合、メッセージにチャネル番号が使われる。

                {fname} へのチャネル活動のログ記録を開始する。
                {fname} が空文字列の場合: ログ記録を停止する。

                {mode} が省略されたか、"a" を含むか、または "o" の場合、ファイ
                ルに追記する。
                {mode} が "w" を含み、"a" を含まない場合、空のファイルから開始
                する。
                {mode} が "o" を含む場合、全ての端末出力をログに記録する。
                それ以外の場合、一部の興味深い端末出力だけがログに記録される。

                ログメッセージを書き込むには ch_log() を使う。ファイルは全て
                のメッセージの後にフラッシュされ、Unix では "tail -f" を使って
                何が起きているかをリアルタイムで見ることができる。

                起動中に端末から何を受信するかを見るために、非常に早い段階でロ
                グを有効にするには、--log を使う (これはモード "ao" を使う):

                        vim --log logfile

                この関数は sandbox では使用できない。
                NOTE: チャネル通信はファイルに保存される、これには機密性の高
                い、およびプライバシーに関わる情報、例えば端末ウィンドウで入力
                したパスワードが含まれる可能性があることに注意すること。

ch_setoptions({handle}, {options})                      ch_setoptions()
                {handle} にオプションを設定する:
                        "callback"      チャネルコールバック
                        "timeout"       ミリ秒単位のデフォルトの読み込みタイムアウト
                        "mode"          チャネル全体のモード
                さらなる説明については ch_open() を参照。
                {handle} はチャネル、またはチャネルを持つジョブにできる。

                Note モードを変更すると、キューに入っているメッセージが失われ
                る可能性があることに注意。

                これらのオプションは変更できない:
                        "waittime"      ch_open() にのみ適用される

                method としても使用できる:
                        GetChannel()->ch_setoptions(options)

                戻り値の型: void

ch_status({handle} [, {options}])                               ch_status()
                {handle} の状態を返す:
                        "fail"          チャネルを開くのに失敗した
                        "open"          チャネルを使用できる
                        "buffered"      チャネルは読み込めるが、書き込めない
                        "closed"        チャネルは使用できない
                {handle} はチャネル、またはチャネルを持つジョブにできる。
                "buffered" は、チャネルが閉じられたが、ch_read() で得られる

                指定する "part" エントリを含めることができる: "out" または
                "err"。例えば、エラー状態を得るには:
                        ch_status(job, {"part": "err"})

                method としても使用できる:
                        GetChannel()->ch_status()

                戻り値の型: String

9. チャネル付きでジョブを開始する                       job-start job

ジョブを開始し、stdin/stdout/stderr のチャネルを開くには:
    let job = job_start(command, {options})

以下でチャネルを得られる:
    let channel = job_getchannel(job)

チャネルは NL モードを使う。別のモードが必要な場合、{options} でこれを指定する
のが最善である。後でモードを変更すると、一部のテキストが既に受信されていて、正
しく解析されないことがある。

コマンドが扱いたい出力行を生成する場合、stdout 用のハンドラを指定する:
    let job = job_start(command, {"out_cb": "MyHandler"})
関数はチャネルおよびメッセージを引数にして呼ばれる。このように定義することにな
る:
    func MyHandler(channel, msg)

ハンドラが無い場合、ch_read() または ch_readraw() で出力を読み込む必要があ
る。これは close コールバック内で行うことができる。read-in-close-cb を参照。

Note 出力を読み込む前にジョブが終了した場合、出力が失われる可能性があることに
注意。これはシステムに依存する (Unix では、パイプの書き込み側を閉じると読み込
み側が EOF を得るためにこれが起こる)。これを避けるには、ジョブが終了する前に少
しの間スリープさせる。

"out_cb" に定義されたハンドラは stderr を受け取らない。それを別に処理したい場
合、"err_cb" ハンドラを追加する:
    let job = job_start(command, {"out_cb": "MyHandler",
            \                     "err_cb": "ErrHandler"})

stderr および stdout の両方を 1 つのハンドラで処理したい場合、"callback" オプ
ションを使う:
    let job = job_start(command, {"callback": "MyHandler"})

システムによっては、ジョブを開始すると Vim がバックグラウンドになり、開始され
たジョブがフォーカスを得ることがある。それを避けるには foreground() 関数を使
う。早い段階で呼ばれたときは常に動作するとは限らない、コールバックハンドラ内に
置くか、またはジョブが開始された後でタイマーを使ってそれを呼ぶ。

ch_evalraw() でコマンドにメッセージを送信できる。チャネルが JSON または JS モー
ドの場合、ch_evalexpr() を使用できる。

使用できるオプションがいくつかある。job-options を参照。
例えば、ジョブを開始し、その出力をバッファ "dummy" に書き込むには:
        let logjob = job_start("tail -f /tmp/log",
                             \ {'out_io': 'buffer', 'out_name': 'dummy'})
        sbuf dummy


バッファからのジョブ入力
                                                        in_io-buffer
バッファから読み込むジョブを実行するには:
        let job = job_start({command},
            \ {'in_io': 'buffer', 'in_name': 'mybuffer'})

                                                        E915 E918
バッファは bufnr() と同様に名前で検索される。job_start() が呼ばれたとき、バッ
ファは存在し、読み込まれていなければならない。

デフォルトでは、これはバッファ全体を読み込む。これは "in_top" および "in_bot"
オプションで変更できる。

特別なモードは、"in_top" が 0 に設定され、"in_bot" が設定されていないときであ
る: バッファに行が追加されるたびに、最後から 2 番目の行がジョブ stdin に送信さ
れる。これにより、最後の行を編集し、Enter を押したときにそれを送信できる。
                                                        channel-close-in
特別なモードを使っていないとき、最後の行が書き込まれた後でパイプまたはソケット
は閉じられる。これは読み込み側に入力が終了したことを伝える。ch_close_in() を
使ってより早く閉じることもできる。

テキスト中の NUL バイトはジョブに渡される (内部的に Vim はこれらを NL バイトと
して保存する)。


close コールバックでジョブ出力を読み込む
                                                        read-in-close-cb
ジョブに時間がかかることがあり、途中の結果が必要無い場合、close コールバックを
追加し、そこで出力を読み込むことができる:

        func! CloseHandler(channel)
          while ch_status(a:channel, {'part': 'out'}) == 'buffered'
            echomsg ch_read(a:channel)
          endwhile
        endfunc
        let job = job_start(command, {'close_cb': 'CloseHandler'})

"echomsg" よりももっと有用なことをしたいだろう。

10. チャネルなしでジョブを開始する                      job-start-nochannel

チャネルを作成せずに別のプロセスを開始するには:
    let job = job_start(command,
        \ {"in_io": "null", "out_io": "null", "err_io": "null"})

これは {command} をバックグラウンドで開始する、Vim はそれが終了するのを待たな
い。

stdin、stdout または stderr のいずれも接続されていないことを Vim が認識すると、
チャネルは作成されない。行き詰まることを避けるために、コマンドにリダイレクトを
含めたいことがよくあるだろう。

使用できるオプションがいくつかある。job-options を参照。

                                                        job-start-if-needed
アドレスへの接続がうまくいかない場合にのみジョブを開始するには、このようなこと
をする:
        let channel = ch_open(address, {"waittime": 0})
        if ch_status(channel) == "fail"
          let job = job_start(command)
          let channel = ch_open(address, {"waittime": 1000})
        endif

Note ch_open() の waittime は、ジョブがポートを使用可能にするのに 1 秒を与える
ことに注意。

11. ジョブ関数                                          job-functions-details

job_getchannel({job})                                    job_getchannel()
                {job} が使用しているチャネルハンドルを得る。
                ジョブがチャネルを持たないかどうかを確認するには:
                        if string(job_getchannel(job)) == 'channel fail'

                method としても使用できる:
                        GetJob()->job_getchannel()

                戻り値の型: channel

job_info([{job}])                                       job_info()
                {job} に関する情報を持つ辞書を返す:
                   "status"     job_status() が返すもの
                   "channel"    job_getchannel() が返すもの
                   "cmd"        ジョブを開始するのに使われたコマンド引数の
                                リスト
                   "process"    プロセス ID
                   "tty_in"     端末入力の名前、無いときは空
                   "tty_out"    端末出力の名前、無いときは空
                   "exitval"    "status" が "dead" のときのみ有効
                   "exit_cb"    終了時に呼ばれる関数
                   "stoponexit" job-stoponexit

                   Unix のみ:
                   "termsig"    プロセスを終了させたシグナル
                                (値については job_stop() を参照)

                   MS-Windows のみ:
                   "tty_type"   使用中の仮想コンソールの種類。
                                値は "winpty" または "conpty"。
                                'termwintype' を参照。

                引数が無い場合、全てのジョブオブジェクトのリストを返す。

                method としても使用できる:
                        GetJob()->job_info()

                戻り値の型: {job} が与えられたかどうかに応じて dict<any> また
                は list<job>


job_setoptions({job}, {options})                        job_setoptions()
                {job} のオプションを変更する。サポートされているものは以下:
                   "stoponexit" job-stoponexit
                   "exit_cb"    job-exit_cb

                method としても使用できる:
                        GetJob()->job_setoptions(options)

                戻り値の型: void


job_start({command} [, {options}])                      job_start()
                ジョブを開始し、ジョブオブジェクトを返す。system() および
                :!cmd とは異なり、これはジョブが終了するのを待たない。
                端末ウィンドウでジョブを開始するには term_start() を参照。

                ジョブの開始に失敗した場合、返されたジョブオブジェクトに対する
                job_status() は "fail" になり、どのコールバックも呼び出され
                ない。

                {command} は文字列にできる。これは MS-Windows で最もうまく動作
                する。Unix では、execvp() に渡すために空白で区切られた部分に分
                割される。二重引用符内の引数は空白を含むことができる。

                {command} はリストにでき、最初の項目が実行可能ファイルで、それ
                以降の項目が引数である。全ての項目は文字列に変換される。これは
                Unix で最もうまく動作する。

                MS-Windows では、job_start() は GUI アプリケーションを非表示に
                する。それを表示したい場合、代わりに :!start を使う。

                コマンドはシェルを通してではなく直接実行され、'shell' オプショ
                ンは使われない。シェルを使うには:
        let job = job_start(["/bin/sh", "-c", "echo hello"])
                または:
        let job = job_start('/bin/sh -c "echo hello"')
                Note これは 2 つのプロセス、シェルおよびそれが実行するコマンド
                を開始することに注意。これを望まない場合、"exec" シェルコマン
                ドを使う。

                Unix では、コマンドにスラッシュが含まれていない場合にのみ、実
                行可能ファイルを検索するのに $PATH が使われる。

                ジョブは Vim と同じ端末を使う。それが stdin から読み込む場合、
                ジョブと Vim が入力を奪い合うことになり、それはうまく動作しな
                い。問題を避けるには stdin および stdout をリダイレクトする:
        let job = job_start(['sh', '-c', "myserver </dev/null >/dev/null"])

                返されたジョブオブジェクトは、job_status() で状態を得るのに、
                および job_stop() でジョブを停止するのに使用できる。

                Note ジョブオブジェクトへの参照が無い場合、それは削除されるこ
                とに注意。これは stdin および stderr を閉じ、ジョブがエラーで
                失敗する原因になることがある。これを避けるには、ジョブへの参照
                を保持する。したがって、以下の代わりに:
        call job_start('my-command')
                以下を使う:
        let myjob = job_start('my-command')
                そして、ジョブが必要なくなったか、または失敗する可能性のある時
                点 (例えば、起動時にメッセージを表示するとき) を過ぎたら
                "myjob" を unlet する。関数にローカルな変数は、関数から戻ると
                存在しなくなることに留意すること。必要な場合、スクリプトローカ
                ル変数を使う:
        let s:myjob = job_start('my-command')

                {options} は辞書でなければならない。それは多くの省略可能な項目
                を含むことができる。job-options を参照。

                method としても使用できる:
                        BuildCommand()->job_start()

                戻り値の型: job


job_status({job})                                       job_status() E916
                {job} の状態を表す文字列を返す:
                        "run"   ジョブは実行中
                        "fail"  ジョブの開始に失敗した
                        "dead"  ジョブは実行後に終了したか、または停止された

                Unix では、存在しないコマンドは "fail" ではなく "dead" になる、
                失敗を検出できる前に fork が起こるためである。

                Vim9 script で、変数が型 "job" で宣言されたが一度も代入されて
                いない場合、その変数を job_status() に渡すと "fail" が返る。

                "exit_cb" オプションで終了コールバックが設定されていて、ジョブ
                が今 "dead" であると検出された場合、コールバックが呼び出され
                る。

                詳細については job_info() を参照。

                method としても使用できる:
                        GetJob()->job_status()

                戻り値の型: String


job_stop({job} [, {how}])                                       job_stop()
                {job} を停止する。これはジョブにシグナルを送るのにも使用でき
                る。

                {how} が省略されたか、または "term" の場合、ジョブは終了させら
                れる。Unix では SIGTERM が送信される。MS-Windows ではジョブは
                強制的に終了させられる ("穏やかな" 方法は無い)。
                これはプロセスグループに送られ、したがって子も影響を受けること
                がある。

                Unix での効果:
                        "term"   SIGTERM (デフォルト)
                        "hup"    SIGHUP
                        "quit"   SIGQUIT
                        "int"    SIGINT
                        "kill"   SIGKILL (最も強い停止方法)
                        number   その番号のシグナル

                MS-Windows での効果:
                        "term"   プロセスを強制終了する (デフォルト)
                        "hup"    CTRL_BREAK
                        "quit"   CTRL_BREAK
                        "int"    CTRL_C
                        "kill"   プロセスを強制終了する
                        その他   CTRL_BREAK

                Unix ではシグナルはプロセスグループに送信される。これは、ジョ
                ブが "sh -c command" の場合、シェルおよびコマンドの両方に影響
                することを意味する。

                結果は数値である: 操作が実行できた場合は 1、そのシステムで
                "how" がサポートされていない場合は 0。
                Note 操作が実行された場合でも、ジョブが実際に停止したかどうか
                は job_status() で確認する必要があることに注意。

                ジョブの状態が "dead" の場合、シグナルは送信されない。これは間
                違ったジョブを停止するのを避けるためである (特に Unix では、プ
                ロセス番号が再利用される)。

                "kill" を使うとき、Vim はジョブが終了すると仮定し、チャネルを
                閉じる。

                method としても使用できる:
                        GetJob()->job_stop()

                戻り値の型: Number

12. ジョブオプション                                    job-options

job_start() の {options} 引数は辞書である。全てのエントリは省略可能である。一
部のオプションは、job_setoptions(job, {options}) を使って、ジョブが開始された
後で使用できる。多くのオプションは、ch_setoptions(channel, {options}) を使っ
て、ジョブに関連するチャネルで使用できる。
job_setoptions() および ch_setoptions() を参照。

                                                in_mode out_mode err_mode
"in_mode"               stdin 専用のモード、パイプを使うときのみ
"out_mode"              stdout 専用のモード、パイプを使うときのみ
"err_mode"              stderr 専用のモード、パイプを使うときのみ
                        値については channel-mode を参照。

                        Note: "mode" を設定すると、部分ごとのモードは上書きさ
                        れる。したがって、先に "mode" を設定し、部分ごとのモー
                        ドを後で設定する。

                        Note: ファイルまたはバッファに書き込むとき、およびバッ
                        ファから読み込むとき、デフォルトで NL モードが使われ
                        る。

                                                job-noblock
"noblock": 1            書き込むとき、非ブロッキングの書き込み呼び出しを使う。
                        これにより、Vim が途中で他のメッセージを処理する必要が
                        ある場合、例えばジョブが Vim にデータを送り返すときに、
                        行き詰まることが避けられる。これは、ch_sendraw() が
                        戻ったときに、まだ全てのデータが書き込まれていないこと
                        があることを意味する。
                        このオプションはパッチ 8.1.0350 で追加された、以下でテ
                        ストする:
                                if has("patch-8.1.350")
                                  let options['noblock'] = 1
                                endif

                                                job-callback
"callback": handler     チャネルのいずれかの部分で読み込むものがあるときのコー
                        ルバック。
                                                job-out_cb out_cb
"out_cb": handler       stdout で読み込むものがあるときのコールバック。チャネ
                        ルがパイプを使うときのみ。"out_cb" が設定されていない
                        場合、チャネルコールバックが使われる。
                        2 つの引数はチャネルおよびメッセージである。

                                                job-err_cb err_cb
"err_cb": handler       stderr で読み込むものがあるときのコールバック。チャネ
                        ルがパイプを使うときのみ。"err_cb" が設定されていない
                        場合、チャネルコールバックが使われる。
                        2 つの引数はチャネルおよびメッセージである。
                                                job-close_cb
"close_cb": handler     チャネルが閉じられたときのコールバック。ch_open() の
                        "close_cb" と同じ、close_cb を参照。
                                                job-drop
"drop": when            いつメッセージを破棄するかを指定する。ch_open() の
                        "drop" と同じ、channel-drop を参照。"auto" について
                        は、exit_cb は考慮されない。
                                                job-exit_cb
"exit_cb": handler      ジョブが終了したときのコールバック。引数はジョブおよび
                        終了ステータスである。
                        Vim は 1 秒間に最大 10 回、終了したジョブを確認する。
                        この確認は job_status() を呼ぶことでも引き起こすこと
                        ができ、その場合 exit_cb ハンドラが呼び出されることが
                        ある。
                        Note データはバッファリングされることがあり、プロセス
                        の終了後もコールバックが呼ばれる可能性があることに注
                        意。
                                                        job-timeout
"timeout": time         ブロックするときに要求を待つ時間、例えば ch_evalexpr()
                        を使うとき。ミリ秒単位。デフォルトは 2000 (2 秒)。
                                                out_timeout err_timeout
"out_timeout": time     stdout のタイムアウト。パイプを使うときのみ。
"err_timeout": time     stderr のタイムアウト。パイプを使うときのみ。
                        Note: "timeout" を設定すると、部分ごとのモードは上書き
                        される。したがって、先に "timeout" を設定し、部分ごと
                        のモードを後で設定する。

                                                job-stoponexit
"stoponexit": {signal}  Vim が終了するときにジョブに {signal} を送る。可能な値
                        については job_stop() を参照。

バッファへの書き込み
                                                        out_io-buffer
out_io または err_io モードが "buffer" で、コールバックがある場合、コールバッ
クを呼び出す前にテキストがバッファに追加される。

バッファが入力および出力の両方に使われる場合、最後の行がチャネル入力に書き込ま
れるものなので、出力行は最後の行の上に置かれる。それ以外の場合、行は最後の行の
下に追加される。

"buffer" で JS または JSON モードを使うとき、ID が 0 または負のメッセージだけ
が、デコード + エンコードの後でバッファに追加される。正の数のメッセージはコー
ルバックによって処理され、コマンドは通常どおり処理される。

"out_name" または "err_name" からのバッファの名前は、既存のバッファのフルネー
ムと比較され、カレントディレクトリに対して名前を展開した後でも比較される。例え
ば、":edit somename" でバッファが作成され、バッファ名が "somename" の場合、そ
のバッファが使われる。

一致するバッファが無い場合、新しいバッファが作成される。常に新しいバッファを作
成するには、空の名前を使う。その後、バッファ番号を得るのに ch_getbufnr() を
使用できる。

新しいバッファでは、'buftype' は "nofile" に、'bufhidden' は "hide" に設定され
る。他の設定が好ましい場合、最初にバッファを作成し、バッファ番号を渡す。
                                        out_modifiable err_modifiable
"out_modifiable" および "err_modifiable" オプションは、'modifiable' オプション
をオフにするため、または 'modifiable' がオフのバッファに書き込むために使用でき
る。これは、行はバッファに追加されるが、ユーザーは簡単にはバッファを変更できな
いことを意味する。
                                        out_msg err_msg
"out_msg" オプションは、新しいバッファの最初の行を
"Reading from channel output..." に設定するかどうかを指定するのに使用できる。
デフォルトではメッセージを追加する。"err_msg" はチャネルエラーに対して同じこと
をする。

'modifiable' がオフの既存のバッファに書き込もうとし、"out_modifiable" または
"err_modifiable" オプションが 0 でない場合、エラーが出て、バッファには書き込ま
れない。

書き込まれるバッファがウィンドウに表示されていて、カーソルが最後の行の最初の桁
にある場合、カーソルは新しく追加された行に移動し、必要な場合はカーソルを表示す
るためにウィンドウが上にスクロールされる。

追加された各行ごとに undo が同期される。NUL バイトは受け付けられる (内部的に
Vim はこれらを NL バイトとして保存する)。


ファイルへの書き込み
                                                        E920
ファイルはパーミッション 600 (ユーザーには読み書き可能、他の人はアクセス不可)
で作成される。これを変更するには setfperm() を使う。

ファイルが既に存在する場合、それは切り詰められる。

13. ジョブを制御する                                    job-control

ジョブの状態を得るには:
        echo job_status(job)

ジョブの実行を停止させるには:
        job_stop(job)

これはジョブを終了させる通常の方法である。Unix では、ジョブに SIGTERM を送る。
ジョブを停止するのに他の方法を使うこと、または任意のシグナルを送ることさえ可能
である。例えば、ジョブを強制的に停止する、"それを kill する" には:
        job_stop(job, "kill")

その他のオプションについては job_stop() を参照。

14. プロンプトバッファを使う                            prompt-buffer

Vim ウィンドウでジョブへの入力を入力したい場合、いくつかの選択肢がある:
- 通常のバッファを使い、全ての可能なコマンドを自分で処理する。
  非常に多くの可能なコマンドがあるので、これは複雑になる。
- 端末ウィンドウを使う。入力したものが直接ジョブに渡り、ジョブ出力が直接ウィン
  ドウに表示される場合、これはうまく動作する。
  terminal-window を参照。
- プロンプトバッファを持つウィンドウを使う。ジョブの (場合によってはフィルタさ
  れた) 出力を表示しながら、Vim でジョブのための行を入力するとき、これはうまく
  動作する。

プロンプトバッファは 'buftype' を "prompt" に設定することで作成される。通常は、
新しく作成したバッファでのみそれを行うだろう。

ユーザーはバッファの一番最後の行で 1 行のテキストを編集し、入力できる。プロン
プト行で Enter を押すと、prompt_setcallback() で設定されたコールバックが呼び
出される。それは通常、行をジョブに送信する。別のコールバックがジョブからの出力
を受け取り、それをバッファ内の、プロンプトの下 (および次のプロンプトの上) に表
示する。

最後の行の、プロンプトの後ろのテキストだけが編集可能である。バッファの残りは
ノーマルモードのコマンドでは変更できない。append() のような関数を呼ぶことで
変更できる。他のコマンドを使うとバッファがめちゃくちゃになることがある。

'buftype' を "prompt" に設定した後、Vim は自動的に挿入モードを開始しない、ユー
ザーが行の入力を始められるように、挿入モードに入りたい場合は :startinsert を
使う。

プロンプトのテキストは prompt_setprompt() 関数で設定できる。
prompt_setprompt() でプロンプトが設定されていない場合、"% " が使われる。バッ
ファの実際のプロンプトテキストは prompt_getprompt() で得られる。

ユーザーはノーマルモードに移ってバッファ内を移動できる。これは古い出力を見る、
またはテキストをコピーするのに便利である。

CTRL-W キーは、次のウィンドウに切り替える CTRL-W w のような、ウィンドウコマン
ドを開始するのに使用できる。これは挿入モードでも動作する (単語を削除するには
Shift-CTRL-W を使う)。ウィンドウを離れると挿入モードは停止される。プロンプト
ウィンドウに戻ってくると挿入モードが復元される。

"a"、"i"、"A" および "I" のような、挿入モードを開始する全てのコマンドは、カー
ソルを最後の行に移動する。"A" は行末に、"I" は行頭に移動する。

これは Unix 用の例である。バックグラウンドでシェルを開始し、次のシェルコマンド
の入力を促す。シェルからの出力はプロンプトの上に表示される。

        " 何が起こるか見られるように、チャネルログを作成する。
        call ch_logfile('logfile', 'w')

        " 入力されたテキストの行を処理する関数。
        func TextEntered(text)
          " Enter を付加してテキストをシェルに送信する。
          call ch_sendraw(g:shell_job, a:text .. "\n")
        endfunc

        " シェルからの出力を処理する関数: それをプロンプトの上に追加する。
        func GotOutput(channel, msg)
          call append(line("$") - 1, "- " .. a:msg)
        endfunc

        " シェルの終了を処理する関数: ウィンドウを閉じる。
        func JobExit(job, status)
          quit!
        endfunc

        " バックグラウンドでシェルを開始する。
        let shell_job = job_start(["/bin/sh"], #{
                \ out_cb: function('GotOutput'),
                \ err_cb: function('GotOutput'),
                \ exit_cb: function('JobExit'),
                \ })

        new
        set buftype=prompt
        let buf = bufnr('')
        call prompt_setcallback(buf, function("TextEntered"))
        eval prompt_setprompt(buf, "shell command: ")

        " シェルコマンドの受け付けを開始する
        startinsert

Vim9 script での同じもの:

        vim9script

        # 何が起こるか見られるように、チャネルログを作成する。
        ch_logfile('logfile', 'w')

        var shell_job: job

        # 入力されたテキストの行を処理する関数。
        def TextEntered(text: string)
          # Enter を付加してテキストをシェルに送信する。
          ch_sendraw(shell_job, text .. "\n")
        enddef

        # シェルからの出力を処理する関数: それをプロンプトの上に追加する。
        def GotOutput(channel: channel, msg: string)
          append(line("$") - 1, "- " .. msg)
        enddef

        # シェルの終了を処理する関数: ウィンドウを閉じる。
        def JobExit(job: job, status: number)
          quit!
        enddef

        # バックグラウンドでシェルを開始する。
        shell_job = job_start(["/bin/sh"], {
                                 out_cb: GotOutput,
                                 err_cb: GotOutput,
                                 exit_cb: JobExit,
                                 })

        new
        set buftype=prompt
        var buf = bufnr('')
        prompt_setcallback(buf, TextEntered)
        prompt_setprompt(buf, "shell command: ")

        # シェルコマンドの受け付けを開始する
        startinsert

15. Language Server Protocol                    language-server-protocol

language server protocol の仕様は以下で入手できる:

    https://microsoft.github.io/language-server-protocol/specification

各 LSP プロトコルメッセージは単純な HTTP ヘッダで始まり、その後に JSON-RPC 形
式でエンコードされたペイロードが続く。これは以下で説明されている:

    https://www.jsonrpc.org/specification

Vim の Dict 内の LSP 要求/通知メッセージを LSP JSON-RPC メッセージにエンコー
ドして送信し、LSP JSON-RPC 応答/通知メッセージを受信して Vim の Dict にデコー
ドするには、channel-mode を "lsp" に設定して LSP サーバーに接続する。

channel-mode が "lsp" に設定されたチャネルで受信したメッセージについて、Vim
は HTTP ヘッダを処理し、JSON-RPC ペイロードを Vim の Dict 型にデコードし、
channel-callback 関数または指定された channel-onetime-callback 関数を呼ぶ。
ch_evalexpr() または ch_sendexpr() 関数を使ってチャネルでメッセージを送信
するとき、Vim は HTTP ヘッダを追加し、Vim の式を JSON にエンコードする。Vim が
組み込み型をどのように JSON にエンコードおよびデコードするかについての詳細は、
json_encode() および json_decode() を参照。

"lsp" モードを使ってチャネルを開くには、ch_open() の {options} 引数の "mode"
項目を "lsp" に設定する。例:

    let ch = ch_open(..., #{mode: 'lsp'})

ジョブで "lsp" モードを使ってチャネルを開くには、job_start() の {options} 引
数の "in_mode" および "out_mode" 項目を "lsp" に設定する。例:

    let cmd = ['clangd', '--background-index', '--clang-tidy']
    let opts = {}
    let opts.in_mode = 'lsp'
    let opts.out_mode = 'lsp'
    let opts.err_mode = 'nl'
    let opts.out_cb = function('LspOutCallback')
    let opts.err_cb = function('LspErrCallback')
    let opts.exit_cb = function('LspExitCallback')
    let job = job_start(cmd, opts)

Note ジョブが stdout に LSP メッセージを、stderr に非 LSP メッセージを出力する
場合、channel-callback 関数が両方のメッセージ形式を適切に処理するべきか、また
は上記のように "out_cb" および "err_cb" にそれらを処理する別々のコールバック関
数を使うべきであることに注意。

JSON-RPC 要求をサーバーに同期的に送信するには、ch_evalexpr() 関数を使う。こ
の関数は待機し、サーバーからのデコードされた応答メッセージを返す。応答の待機時
間を制御するには、channel-timeout または {options} 引数の "timeout" フィール
ドのどちらかを使用できる。要求がタイムアウトした場合、空の Dict が返される。
例:

    let req = {}
    let req.method = 'textDocument/definition'
    let req.params = {}
    let req.params.textDocument = #{uri: 'a.c'}
    let req.params.position = #{line: 10, character: 3}
    let defs = ch_evalexpr(ch, req, #{timeout: 100})
    if defs->empty()
        ... <失敗を処理する>
    endif

Note 要求メッセージでは "id" フィールドを指定するべきではないことに注意。それ
が指定された場合、Vim はその値を内部で生成された識別子で上書きする。Vim は現
在、"id" フィールドには数値型のみをサポートしている。
コールバック関数は、成功した RPC 要求および失敗した RPC 要求の両方に対して呼び
出される。

JSON-RPC 要求をサーバーに送信し、応答を非同期に処理するには、ch_sendexpr()
関数を使い、コールバック関数を与える。要求メッセージに "id" フィールドが存在す
る場合、Vim はそれを内部で生成された番号で上書きする。この関数は、メッセージに
使われた識別子を持つ Dict を返す。これは LSP サーバーにキャンセル要求を送信す
るのに使用できる (必要な場合)。例:

    let req = {}
    let req.method = 'textDocument/hover'
    let req.id = 200
    let req.params = {}
    let req.params.textDocument = #{uri: 'a.c'}
    let req.params.position = #{line: 10, character: 3}
    let resp = ch_sendexpr(ch, req, #{callback: 'HoverFunc'})

ch_sendexpr() 関数を使ってサーバーに送信した未処理の非同期 LSP 要求をキャン
セルするには、その要求に対して ch_sendexpr() 関数が返した ID を付けて、
ch_sendexpr() 関数を使ってキャンセルメッセージをサーバーに送信する。例:

    " 補完要求を送信する
    let req = {}
    let req.method = 'textDocument/completion'
    let req.params = {}
    let req.params.textDocument = #{uri: 'a.c'}
    let req.params.position = #{line: 10, character: 3}
    let reqstatus = ch_sendexpr(ch, req, #{callback: 'LspComplete'})
    " キャンセル通知を送信する
    let notif = {}
    let notif.method = '$/cancelRequest'
    let notif.id = reqstatus.id
    call ch_sendexpr(ch, notif)

JSON-RPC 通知メッセージをサーバーに送信するには、ch_sendexpr() 関数を使う。
サーバーは通知に対して応答メッセージを送信しないので、"callback" 項目を指定し
ない。例:

    call ch_sendexpr(ch, #{method: 'initialized'})

サーバーからの JSON-RPC 要求メッセージに応答するには、ch_sendexpr() 関数を使
う。応答メッセージでは、サーバーの要求メッセージから "id" フィールドの値をコ
ピーする。例:

    let resp = {}
    let resp.id = req.id
    let resp.result = 1
    call ch_sendexpr(ch, resp)

サーバーからの JSON-RPC 通知メッセージは channel-callback 関数を通して配信さ
れる。

ユースケースに応じて、同じチャネルで ch_evalexpr()、ch_sendexpr() および
ch_sendraw() 関数を使用できる。

LSP 要求メッセージは以下の形式を持つ (Vim の Dict として表現)。"params" フィー
ルドは省略可能である:

    {
        "jsonrpc": "2.0",
        "id": <number>,
        "method": <string>,
        "params": <list|dict>
    }

LSP 応答メッセージは以下の形式を持つ (Vim の Dict として表現)。"result" および
"error" フィールドは省略可能である:

    {
        "jsonrpc": "2.0",
        "id": <number>,
        "result": <vim type>
        "error": <dict>
    }

LSP 通知メッセージは以下の形式を持つ (Vim の Dict として表現)。"params" フィー
ルドは省略可能である:

    {
        "jsonrpc": "2.0",
        "method": <string>,
        "params": <list|dict>
    }

16. Debug Adapter Protocol                      debug-adapter-protocol

debug adapter protocol は language server protocol に非常に似ており、主な違い
は JSON-RPC 形式を使わないことである。仕様はここで見つけられる:

    https://microsoft.github.io/debug-adapter-protocol/specification

このプロトコルは LSP プロトコルと同じヘッダ形式を使う。

Vim の Dict 内の DAP 要求/通知メッセージを JSON メッセージにエンコードして送
信し、DAP JSON 応答/通知メッセージを受信して Vim の Dict にデコードするには、
channel-mode を "dap" に設定してデバッグアダプタに接続する。

channel-mode が "dap" に設定されたチャネルで受信したメッセージについて、Vim
は HTTP ヘッダを処理し、JSON ペイロードを Vim の Dict 型にデコードする。
ch_evalexpr() または ch_sendexpr() 関数を使ってチャネルでメッセージを送信
するとき、Vim は HTTP ヘッダを追加し、Vim の式を JSON にエンコードする。

Vim は JSON DAP メッセージに "seq" フィールドを自動的に追加し、応答については
"request_seq" フィールドも管理する。しかし、"type" フィールドは追加しない、そ
れは Dict 内で手動で指定するべきである。

それ以外の点では、動作は Vim が "lsp" チャネルモード
language-server-protocol を扱う方法と同じである。

==============================================================================
17. Model Context Protocol                      model-context-protocol

{ViAI のみ}

model context protocol の仕様は以下で入手できる:

    https://modelcontextprotocol.io/specification

MCP メッセージは、LSP メッセージと同様に JSON-RPC メッセージであるが、ヘッダな
しで送信される: 各メッセージは NL で終わる 1 行の JSON である。これは MCP の
stdio トランスポートであり、HTTP トランスポートはサポートされていない。

MCP メッセージを送受信するには、channel-mode を "mcp" に設定する。それ以外の
点では、メッセージは "lsp" チャネルモードと同様に処理される、
language-server-protocol を参照。受信したメッセージは JSON の値が終わるとこ
ろで終わるので、複数行にわたる JSON も受け付けられる。JSON-RPC バッチのような、
JSON オブジェクトでないものは破棄される。

MCP サーバーになるには、--stdio-channel 付きで Vim を開始し、"mcp" モードで
チャネルを開く、channel-stdio を参照:
        func OnMessage(ch, msg)
          if a:msg.method == 'ping'
            call ch_sendexpr(a:ch, #{id: a:msg.id, result: {}})
          endif
        endfunc
        let ch = ch_open('stdio', #{mode: 'mcp', callback: 'OnMessage'})

MCP サーバーと通信するには、それをジョブとして開始する:
        let job = job_start(cmd, #{in_mode: 'mcp', out_mode: 'mcp'})
        let resp = ch_evalexpr(job, #{method: 'tools/list', params: {}})

Vim は "initialize" のような、プロトコル自体のメッセージを処理しない、スクリプ
トがしなければならない。
